# 平台统一现金与出珠架构 V2.2

V2.2 的核心目标是减少状态和事件类型：现金事实由平台统一结算，出珠只保留单活动订单、单 Progress、单 durable Terminal。

## 分层

```text
平台订单/现金会话
-> MQTT 命令
-> Android SQLite active_physical_order
-> ttyS5 DispenseStartOrder
-> 控制板单 DispenseOrder 状态机
-> DispenseTerminal
-> Android command-result outbox
-> DispenseTerminalAck
```

设备不得根据本地现金金额、支付页面或本地规则自行决定出珠数量。唯一物理出珠授权仍是平台 `dispense_marbles`。

## Android 单订单状态机

状态只使用：

- `IDLE`：无 `active_physical_order`。
- `DISPENSING`：已保存 active order，已关闭现金，正在等待控制板 Terminal。
- `FINISHING`：已保存 Terminal 和 command-result outbox，正在等待 `DispenseTerminalAck` 线路 echo。
- `BLOCKED`：零出珠、部分出珠、无珠、超时或硬件异常，禁止现金和下一单。

事务要求：

1. 创建订单时在同一 SQLite 事务内读取并递增 `next_order_sequence`、保存 command、插入 `active_physical_order`。
2. 存在 active order 时，下一笔平台出珠命令立即失败：`PREVIOUS_PHYSICAL_ORDER_ACTIVE`，不得发送 `DispenseStartOrder`。
3. 收到 Terminal 后，先保存原始终态证据，再生成或复用 command-result eventNo/outbox。
4. SQLite 提交成功后才发送 `DispenseTerminalAck`。
5. `DispenseTerminalAck` 获得线路 echo 后，成功订单才能清除 active order 并允许下一单。

App 重启：

- 无 active order：按现金配置恢复。
- `DISPENSING`：禁止现金和下一单，不重发 Start，等待控制板重复 Terminal。
- `FINISHING`：复用原 `orderSequence + terminalFrameId` 重发 TerminalAck。
- `BLOCKED`：保持现金关闭，等待维护。

## 控制板单订单状态机

控制板状态：

- `IDLE`
- `RUNNING`
- `WAIT_TERMINAL_ACK`
- `BLOCKED`

规则：

- 只有 `IDLE` 接受新 `DispenseStartOrder`。
- `RUNNING` 达到 requested 后停止电机并生成成功 Terminal。
- 超时、无珠、故障停止电机并生成失败 Terminal，actual 保留真实 PD4 累计。
- `WAIT_TERMINAL_ACK` 持续重发同一 Terminal，直到 ACK 精确匹配 `orderSequence + terminalFrameId`。
- 成功 Terminal 被确认后回 `IDLE`。
- 失败、零出珠、部分出珠被确认后进入 `BLOCKED`。
- 补珠或人工复位后才回 `IDLE`。

不再使用 durable Started，也不再使用 V2.1 的 Completed/Failed 多事件。

## 协议

Android -> Board：

| Code2 | 名称 | 数据 |
|---:|---|---|
| `0x30` | DispenseStartOrder | Data1:2=orderSequence16，Data3:4=requestedQuantity16 |
| `0x31` | DispenseTerminalAck | Data1:2=orderSequence16，Data3=terminalFrameId，Data4=0 |
| `0x33` | CashAcceptanceApplyV22 | Data1=现金 mask，Data2:4=configVersion24 |

Board -> Android：

| Code2 | 名称 | 数据 |
|---:|---|---|
| `0x40` | DispenseProgress | Data1:2=orderSequence16，Data3:4=actualQuantity16 |
| `0x41` | DispenseTerminal | Data1:2=orderSequence16，Data3:4=actualQuantity16，ExpandCode=resultCode |

`Progress` 非可靠，只用于 UI。成功只看 `Terminal`：

```text
controllerResultCode == 0
terminalActual > 0
terminalActual == requestedQuantity
```

旧 V2.1 物理协议不兼容。旧现金启用命令不能启用现金，只有 `0x33` 可启用。

## 现金门禁

订单创建后立即关闭现金。

允许启用现金必须同时满足：

- 无 active order；
- 非 BLOCKED；
- 库存和控制板状态允许；
- 现金配置有效。

以下状态保持现金关闭：

- `DISPENSING`
- `FINISHING`
- `BLOCKED`
- TerminalAck 未获得 echo
- App 重启恢复 active order

## UI 动画

Android 广播 `ACTION_DISPENSE_ORDER_EVENT`：

| eventType | 含义 |
|---|---|
| `started` | active order 事务提交后，显示出珠动画 |
| `progress` | 更新 actual/requested |
| `finished` | Terminal 已持久化，停止动画并显示完成 |
| `blocked` | 停止动画，显示维护提示 |
| `recovering` | App 重启发现 active order，显示恢复提示，不播放重新开始效果 |

## 存珠

存珠保留为本地维护功能：

- 保留存珠电机、PD3 光眼、库存更新和补珠入口。
- 不使用平台订单 `orderSequence`。
- 不发布平台订单 Terminal。
- 出珠订单非 IDLE 时禁止存珠维护。

光眼映射固定：

- PD4 / EXTI4 -> 出珠光眼 -> `HoolleOutput_Pin` -> `Hardware_OnDispensePulse`
- PD3 / EXTI3 -> 存珠光眼 -> `CardFeedback_Pin` -> `Hardware_OnCollectPulse`

## 发布顺序

控制板和 Android 必须成套发布到 V2.2。V2.1 App 与 V2.2 控制板不得混用，避免旧 token 帧被误解释为新订单帧。

## V2.2 安全补充

- Android 必须先确认控制板 `VersionReport >= 0x02020000`（2.2.0.0），才允许现金启用和平台出珠。
- 版本未知或版本过低时，Android 仅使用旧 `0x18 CashAcceptanceApply(mask=0)` 做兼容现金关闭；不得发送启用请求，不得创建 active order，不得发送 `DispenseStartOrder`。
- 版本确认后，现金启用和关闭统一使用 `0x33 CashAcceptanceApplyV22`。
- `active_physical_order` 保存原始 MQTT source topic，App 重启后用该 topic 恢复 SDK command 上下文；旧数据缺少 topic 时进入 `BLOCKED/MANUAL_REVIEW`，不确认 Terminal。
- Terminal 永久缺失时，平台 command-result 闭环为 `failed/CONTROLLER_TERMINAL_MISSING`；`actualQuantity` 使用最后观察到的 `lastProgressActual`，不保证最终真实数量。
- Terminal 缺失后设备保持 `BLOCKED`，现金保持关闭，禁止下一单。
- 迟到 Terminal 只作为原始证据保存并发送精确 `DispenseTerminalAck`，用于停止控制板重发；不得覆盖已发布或已入 outbox 的 unknown 结果，不得生成第二个 command-result。
- `DispenseTerminalAck` 线路 echo 前，成功订单不得解锁下一单。
