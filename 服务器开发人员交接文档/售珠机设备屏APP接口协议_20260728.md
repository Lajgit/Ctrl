# 售珠机设备屏 APP 接口协议

> 2026-08-01 更新：设备扫码购珠支持仅配置会员小程序和微信商户号，不再强制要求公众号；线上购珠继续兼容公众号微信支付和支付宝聚合扫码。

## 1. 定位

售珠机设备屏 APP 是设备上的顾客自助交易终端，不是会员小程序，也不是商家管理端。

它负责：

1. 展示设备、门店、购珠档位和当前可用功能；
2. 承载扫码购珠、现金购珠、会员存取珠、套餐核销等顾客交互；
3. 将扫码结果或顾客选择交给后端业务接口；
4. 展示后端返回的交易状态，不自行决定订单、退款或最终交付结果。

硬件控制仍使用 MQTT。现金事件仍由验钞器确认后通过 MQTT 上报，设备 APP 不为现金交易预先创建订单。

## 2. 当前阶段

已实现设备屏首页、微信/支付宝聚合扫码购珠、会员取珠、会员存珠小程序入口、平台套餐核销和积分商城小程序入口：

`POST /api/device/app/bootstrap`

`POST /api/device/app/purchase/native/create`

`POST /api/device/app/purchase/native/status`

`POST /api/device/app/member/withdrawal/create`

`POST /api/device/app/member/withdrawal/status`

`POST /api/device/app/redemption/internal/create`

`POST /api/device/app/redemption/internal/status`

接口返回：

- 设备和门店展示信息；
- 顶部宣传图片/视频、购珠区文案和首页配置刷新周期；
- 门店当前可用的线上购珠规则及固定价格档位；
- 设备当前已经确认应用的现金配置快照；
- 会员存珠小程序入口码；
- 积分商城小程序入口码；
- 首页各业务入口的真实可用状态和不可用原因；
- 依赖服务局部降级信息。

当前未实现的能力不会伪装为可用：

- 美团、抖音、快手等第三方团购核销。SDK 已支持按 bootstrap 路由配置识别设备路由码并调用统一接口；正式渠道 Adapter、账号、门店和商品映射就绪前，入口仍必须禁用。

## 3. 请求签名

接口通过网关匿名放行，但业务服务必须校验设备签名。客户端不得传入或决定租户 ID。

请求体：

```json
{
  "deviceNo": "VMAPP0001",
  "appVersion": "1.0.0",
  "timestamp": 1785225600000,
  "nonce": "device-app-nonce-0001",
  "signature": "Base64Url-HMAC-SHA256"
}
```

签名原文：

```text
device-app|v1|bootstrap|{deviceNo}|{timestamp}|{nonce}|{appVersion}
```

签名规则：

1. `deviceNo` 使用平台标准化后的设备通信编号；
2. `timestamp` 为毫秒时间戳，与服务端时间差不得超过 5 分钟；
3. `nonce` 长度为 16 到 64，只允许字母、数字、下划线和短横线；
4. 密钥使用设备激活接口返回的当前设备通信密钥；
5. 算法为 `HmacSHA256`，结果推荐使用无填充 Base64Url；服务端同时接受小写十六进制；
6. 同一设备的同一 `nonce` 在 10 分钟内只能使用一次；
7. `appVersion` 必须与请求中的值完全一致，不允许包含空格或竖线。

### 3.1 聚合扫码购珠创建签名

签名原文：

```text
device-app|v1|native-purchase-create|{deviceNo}|{timestamp}|{nonce}|{clientRequestNo}|{purchaseRuleId}|{priceTierId}|{purchaseQuantity}
```

`priceTierId` 与 `purchaseQuantity` 必须且只能填写一个，未填写的字段在签名原文中保留为空字符串。

请求示例：

```json
{
  "deviceNo": "VMAPP0001",
  "timestamp": 1785225600000,
  "nonce": "device-app-nonce-0002",
  "signature": "Base64Url-HMAC-SHA256",
  "clientRequestNo": "APPREQ_20260728_0001",
  "purchaseRuleId": 301,
  "priceTierId": 401,
  "purchaseQuantity": null
}
```

`clientRequestNo` 由设备 APP 生成，长度为 16 到 64，只允许字母、数字、下划线和短横线。同一请求号重复提交必须使用完全相同的计价参数，服务端会返回同一订单和支付流水。

创建成功后，APP 使用 `scanUrl` 在本地渲染付款二维码，不应把它上传到第三方二维码服务，也不得按 URL 域名或协议自行改写。当微信 Native 可用且公众号、支付宝入口均不可用时，`scanUrl` 是微信返回的 `weixin://wxpay/...`；Native 不可用时回退为一次性小程序 URL Link；存在公众号微信支付或支付宝时，`scanUrl` 为服务端聚合扫码地址。

关键支付字段：

- `paymentMode`：微信 Native 直付为 `DIRECT_SCAN`，聚合扫码或小程序入口为 `AGGREGATE_SCAN`；
- `scanUrl`：设备屏应原样渲染的二维码内容，可能是微信 Native `weixin://wxpay/...`、聚合扫码地址或微信小程序 URL Link；
- `supportedChannels`：当前会话真实可用的支付入口，可能包含 `WECHAT_NATIVE`、`WECHAT_MINIAPP`、`WECHAT_JSAPI`、`ALIPAY_PRECREATE`；
- `codeUrl`：保留字段，当前设备统一读取 `scanUrl`，该字段为空；
- `payChannel`：订单在未选定真实支付渠道前可能为 `DEVICE_AGGREGATE_SCAN`，支付选路后以服务端状态为准。

`WECHAT_MINIAPP` 只表示二维码进入会员小程序，不是订单支付流水的最终渠道。会员在小程序认领订单后，订单渠道切换为现有 `WECHAT_JSAPI`，支付成功、退款和设备出珠仍走原有后端状态机。

`WECHAT_NATIVE` 表示设备二维码直接付款，订单和支付流水的最终渠道均为 `WECHAT_NATIVE`。它不需要公众号网页授权或用户 OpenId；设备仍只能轮询业务状态，并等待后端 MQTT 出珠指令。

### 3.2 聚合扫码购珠状态签名

签名原文：

```text
device-app|v1|native-purchase-status|{deviceNo}|{timestamp}|{nonce}|{clientRequestNo}
```

状态查询只能查询当前签名设备创建的订单，不能通过客户端租户 Header 或订单号跨设备查询。

### 3.3 会员取珠创建签名

签名原文：

```text
device-app|v1|member-withdrawal-create|{deviceNo}|{timestamp}|{nonce}|{clientRequestNo}|{withdrawalCode}
```

请求示例：

```json
{
  "deviceNo": "VMAPP0001",
  "timestamp": 1785225600000,
  "nonce": "device-app-nonce-0003",
  "signature": "Base64Url-HMAC-SHA256",
  "clientRequestNo": "APPWITHDRAW_20260729_0001",
  "withdrawalCode": "W2082295280346042368"
}
```

`withdrawalCode` 必须是会员小程序生成的 `W` 前缀一次性取珠码。设备 APP 不得保存、回显或记录完整取珠码；同一 `clientRequestNo` 重试时必须继续使用原取珠码，换码复用请求号会被拒绝。

### 3.4 会员取珠状态签名

签名原文：

```text
device-app|v1|member-withdrawal-status|{deviceNo}|{timestamp}|{nonce}|{clientRequestNo}
```

状态查询按租户、签名设备、客户端请求号和会员取珠操作类型共同绑定，不返回会员 ID、会员取珠码、账户交易号、预占号或设备操作令牌。

### 3.5 平台套餐核销创建签名

签名原文：

```text
device-app|v1|internal-redemption-create|{deviceNo}|{timestamp}|{nonce}|{clientRequestNo}|{pickupCode}
```

`pickupCode` 必须是平台订单生成的六位数字取珠码。设备 APP 不得保存、回显或记录完整取珠码；同一 `clientRequestNo` 重试时必须继续使用原取珠码，换码复用请求号会被拒绝。

### 3.6 平台套餐核销状态签名

签名原文：

```text
device-app|v1|internal-redemption-status|{deviceNo}|{timestamp}|{nonce}|{clientRequestNo}
```

状态查询按租户、签名设备、客户端请求号和内部核销操作类型共同绑定，不返回套餐订单、凭证、预占号或设备操作令牌。

## 4. 关键响应语义

### 4.1 presentation

`presentation` 是设备屏首页展示配置，来源于 `device_machine.config.deviceApp`。未配置时服务端返回默认文案、300 秒刷新周期和空宣传素材列表，APP 不应自行写死另一套默认业务文案。

设备配置示例：

```json
{
  "deviceApp": {
    "refreshIntervalSeconds": 300,
    "purchaseSection": {
      "title": "购珠套餐",
      "description": "选择套餐后扫码支付，也可按提示投入纸币购珠"
    },
    "heroMedia": [
      {
        "type": "VIDEO",
        "url": "https://cdn.example.com/promo.mp4",
        "coverUrl": "https://cdn.example.com/promo-cover.jpg",
        "sortOrder": 10,
        "durationSeconds": 15
      },
      {
        "type": "IMAGE",
        "url": "https://cdn.example.com/banner.jpg",
        "sortOrder": 20,
        "durationSeconds": 10
      }
    ],
    "features": {
      "MEMBER_WITHDRAW": {
        "visible": true,
        "title": "会员取珠",
        "description": "扫描会员取珠码",
        "icon": "member-withdraw",
        "sortOrder": 30
      },
      "THIRD_PARTY_REDEMPTION": {
        "visible": false
      }
    }
  }
}
```

约束：

1. `refreshIntervalSeconds` 范围为 30 至 3600，APP 按此周期重新调用 `bootstrap`；
2. `heroMedia.type` 支持 `IMAGE`、`VIDEO`，素材地址和封面地址只接受 HTTP/HTTPS；最多返回 20 个素材并按 `sortOrder` 升序排列；
3. 图片未配置 `durationSeconds` 时默认展示 10 秒，视频未配置时由 APP 按媒体实际时长播放；
4. 功能入口只允许覆盖 `title`、`description`、`icon`、`sortOrder`、`visible`；配置中的其他字段不会改变业务状态；
5. `available`、`unavailableReason` 和 `interactionMode` 是后端权威结果。配置不能把未授权、未配置支付、设备离线或尚未实现的功能强行开启；
6. 非法字段会局部使用默认值，并在 `degradedMessages` 中返回“设备屏展示配置部分无效，已使用默认值”。

### 4.2 purchaseRules

`purchaseRules` 是商品与定价服务返回的服务端可信定价配置。APP 只能使用返回的 `purchaseRuleId` 和 `priceTierId` 发起后续购珠请求，不得自行上传金额。

设备屏与会员小程序共用 `marble_purchase_rule` 和 `marble_purchase_price_tier`。设备屏通过商品服务读取门店可用配置，会员小程序通过同一业务服务读取；创建订单时服务端仍按同一规则重新报价，不信任客户端金额。

### 4.3 cashSale

`cashSale` 读取设备已经确认应用的不可变现金配置快照，而不是商家刚编辑但尚未同步到设备的新配置。

响应示例：

```json
{
  "cashSale": {
    "available": true,
    "unavailableReason": null,
    "configurationVersion": 3,
    "itemId": 501,
    "itemCode": "MARBLE",
    "itemName": "弹珠",
    "unitName": "珠",
    "tiers": [
      {
        "cashMediumType": 1,
        "cashMediumCode": "banknote",
        "cashMediumName": "纸币",
        "denominationAmount": 500,
        "marbleQuantity": 5,
        "tierNo": "CASH-5"
      }
    ]
  }
}
```

`cashSale` 字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `available` | `boolean` | 当前设备是否允许现金购珠；设备 APP 只在该值为 `true` 时开放现金入口 |
| `unavailableReason` | `string/null` | 不可用原因；可用时为 `null` |
| `configurationVersion` | `long/null` | 设备已经回执确认应用的现金配置版本，不是商家端待下发版本 |
| `itemId` | `long/null` | 本次现金配置对应的商品 ID |
| `itemCode` | `string/null` | 商品编码 |
| `itemName` | `string/null` | 商品名称 |
| `unitName` | `string/null` | 出珠数量单位，例如“珠” |
| `tiers` | `array` | 已应用配置中的现金面额与出珠数量映射；没有有效快照时返回空数组 |

`cashSale.tiers[]` 字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `cashMediumType` | `integer` | 现金介质类型：`1` 纸币、`2` 硬币 |
| `cashMediumCode` | `string` | 设备协议介质编码：`banknote` 或 `coin` |
| `cashMediumName` | `string` | 现金介质展示名称 |
| `denominationAmount` | `integer` | 面额，单位为分；`500` 表示 5 元 |
| `marbleQuantity` | `integer` | 接收一张纸币或一枚硬币后应出珠的数量 |
| `tierNo` | `string` | 已应用现金档位编号，现金事件上报时作为配置快照定位字段 |

只有同时满足以下条件时 `cashSale.available=true`：

1. 设备获得直接购珠授权；
2. 现金接收已开启；
3. 服务端发布版本与设备确认应用版本完全一致，并存在至少一个已应用现金档位；
4. 设备在线且运行状态为空闲；
5. Account 域门店可用物料库存能够覆盖已应用档位中的最大出珠数量。

库存检查失败时按故障关闭处理：库存未初始化返回“门店物料库存尚未初始化”，库存不足返回“门店可用
物料库存不足”，库存服务异常返回“门店物料库存查询暂不可用”。这次查询只决定当前入口，不冻结库存；
现金进入钱箱后的原子库存预占仍是最终校验，因此设备不得把一次 `available=true` 长期缓存为库存承诺。

配置已应用但设备当前离线或忙碌时，接口仍返回 `configurationVersion`、商品和 `tiers`，同时返回 `available=false` 及运行时不可用原因。未授权、现金接收未开启或尚无已应用版本时，配置字段可能为 `null`，`tiers` 返回空数组。设备不得使用商家端编辑值、本地旧缓存或金额自行推导出珠数量。

现金状态分为两个事实源，设备 APP 不得混用：

| 状态 | 权威来源 | 用途 |
| --- | --- | --- |
| 商家是否开启现金接收 | MQTT `sync_cash_configuration.data.cashAcceptanceEnabled` | 持久化现金配置并控制验钞器的配置开关 |
| 当前是否允许操作现金购珠 | HTTP `cashSale.available` 或 `features[code=CASH_PURCHASE].available` | 控制当前入口和运行门控 |

`cashSale.available=false` 不能直接展示为“商家关闭现金”。APP 必须读取
`unavailableReason`：例如“设备通信离线”或“门店可用物料库存不足”都表示商家配置仍可能开启，只是
当前运行条件不满足。
同理，`available=true` 也不能替代 MQTT 配置持久化；设备没有完整持久化并成功应用对应
`sync_cash_configuration` 版本时不得开启验钞器。

设备启动时先完成 MQTT 连接、订阅、心跳和状态上报，再请求或刷新 bootstrap。MQTT 断开、设备
进入忙碌或故障状态时，APP 应立即关闭现金入口；恢复在线和空闲后重新请求 bootstrap，不得使用
上一次的 `available=true` 持续营业。

服务端会在现金规则、现金档位或 `DIRECT_PURCHASE` 授权变化后自动重算设备有效现金配置。若有效
载荷变化，会通过 MQTT 下发一个更高 `configVersion` 的完整 `sync_cash_configuration` 指令；授权
撤销、授权到期、规则停用或没有任何可用面额时，下发 `cashAcceptanceEnabled=false` 且
`cashSaleItems=[]`。授权或规则恢复后再下发新的启用版本。

变化消息用于及时触发，Device 服务的定时游标扫描用于覆盖消息丢失、授权时间自然跨界和服务重启。
因此设备无需轮询商家配置，也不得自行调用 Product 规则接口。设备收到新版本后必须整体替换本地配置，
在完整持久化并完成硬件应用前保持验钞器关闭；收到重复版本或重复 `messageId` 时按本地幂等结果重发
终态，不重复执行硬件动作。

### 4.4 features

首页入口由服务端返回，APP 根据数组顺序或 `sortOrder` 排列，根据 `visible` 决定是否展示，根据 `available` 决定是否允许操作。`icon` 是与设备 APP 图标资源约定的稳定标识，`unavailableReason` 应直接用于禁用提示。

当前入口包括：

| code | 交互方式 | 当前说明 |
| --- | --- | --- |
| `ONLINE_PURCHASE` | `AGGREGATE_SCAN` | 设备、计价规则及微信或支付宝至少一个渠道可用时允许操作 |
| `CASH_PURCHASE` | `CASH_ACCEPTOR` | 使用已应用现金配置和 MQTT 现金事件 |
| `MEMBER_WITHDRAW` | `SCAN_MEMBER_CODE` | 扫描会员取珠码 |
| `MEMBER_DEPOSIT` | `SHOW_MINIAPP_QR` | 展示设备专属会员存珠入口码，结果由会员小程序按业务单查询 |
| `INTERNAL_REDEMPTION` | `SCAN_REDEMPTION_CODE` | 扫描平台取珠凭证 |
| `THIRD_PARTY_REDEMPTION` | `SCAN_THIRD_PARTY_CODE` | 美团/抖音/快手渠道适配完成前不可操作 |
| `POINTS_MALL` | `SHOW_MINIAPP_QR` | 展示门店积分商城小程序码；入口码可用时开放，不受设备在线或空闲状态影响 |

### 4.5 核销码扫码路由

`redemptionRouting` 是设备识别会员取珠、平台套餐核销和第三方核销二维码的服务端路由配置。设备 APP 不得内置 `W`、`XD:1:PICKUP:`、美团、抖音或快手前缀，也不得根据码长度、纯数字特征或历史缓存猜测业务类型或渠道。

内部码规则：

| 功能 | 二维码内容 | `stripPrefix` | 提交给业务接口的原始码 |
| --- | --- | --- | --- |
| `MEMBER_WITHDRAW` | `W2082295280346042368` | `false` | `W2082295280346042368` |
| `INTERNAL_REDEMPTION` | `XD:1:PICKUP:123456` | `true` | `123456` |

会员取珠码的 `W` 是原始业务码的一部分，不能剥离。平台套餐二维码的 `XD:1:PICKUP:` 是二维码协议头，设备匹配后必须剥离，HTTP `pickupCode` 仍只提交六位数字。手工输入六位取珠码继续调用原始码方法，不经过二维码前缀匹配。

第三方扫码后依次执行：

1. 使用本次 `bootstrap` 返回的 `thirdPartyChannels` 精确匹配 `voucherCodePrefix`；
2. 未匹配到、匹配到多个规则或前缀后没有原始码时，直接提示二维码不支持，不调用核销接口；
3. 匹配成功后剥离前缀，将对应 `channelCode` 和原始 `voucherCode` 分字段提交；
4. 任意内部或第三方路由发生变化时递增 `routingVersion`；设备发现版本变化后立即整体替换本地缓存，不合并新旧版本；
5. `THIRD_PARTY_REDEMPTION.available=false` 时，即使存在路由配置也不得开放扫码入口。

前缀只用于减少误扫和错误分类，不是安全凭证。用户可以自行构造带前缀字符串，因此服务端仍必须验证设备签名、渠道配置、门店映射、商品映射和第三方券真实性。

### 4.6 小程序入口

`memberEntryScene` 是设备专属会员存珠入口，微信小程序解析后进入 `pages/marble-deposit/marble-deposit`，存珠业务创建、状态查询和 MQTT 收珠均由会员小程序与后端完成。

`pointsMallEntryScene` 是门店级稳定积分商城入口，微信小程序解析 `POINTS_MALL` 后进入 `pages/mall/mall`。积分余额、礼品兑换和兑换码仍由会员小程序处理，设备屏只展示二维码。两类入口不可混用；存珠码固定携带设备目标，积分商城码只绑定门店。

## 5. 降级原则

门店无效时整个启动失败，避免设备在错误商家或错误门店营业。

套餐价格服务、会员存珠入口码或积分商城入口码服务暂时不可用时，接口仍返回设备首页的其他能力，并在 `degradedMessages` 中说明；对应功能入口必须禁用。

支付服务会在首页启动时分别校验会员小程序微信支付、公众号微信支付和支付宝扫码支付。所有入口均不可用时，`ONLINE_PURCHASE.available=false`；至少一个入口可用时开放线上购珠。具体 `supportedChannels` 在创建支付会话后返回，不会伪装未配置或未成功生成的入口。

## 6. 聚合扫码购珠状态

| purchaseStatus | terminal | 含义 | APP 行为 |
| --- | --- | --- | --- |
| `WAITING_PAYMENT` | `false` | 等待顾客扫码付款 | 展示二维码并轮询 |
| `EXPIRED` | `false` | 二维码支付窗口已过期，服务端正在确认并关闭支付 | 保持轮询，等待 `CLOSED` 或支付结果 |
| `DISPENSING` | `false` | 支付成功，订单域已启动设备出珠 | 隐藏二维码，展示出珠中 |
| `COMPLETED` | `true` | 设备全量出珠并已确认履约 | 展示成功 |
| `REFUNDING` | `false` | 出珠异常，订单正在退款 | 展示处理中，禁止重复支付 |
| `REFUNDED` | `true` | 已原路退款 | 展示退款结果 |
| `CANCELED` | `true` | 订单已取消 | 退出当前支付页 |
| `CLOSED` | `true` | 超时关单完成 | 允许使用新请求号重新选择套餐 |

APP 不得因为看到微信或支付宝付款成功页就自行出珠。只有服务端订单进入已支付待履约状态后，订单域才会通过现有设备操作单启动出珠。

## 7. 会员取珠状态

| withdrawalStatus | terminal | 含义 | APP 行为 |
| --- | --- | --- | --- |
| `DISPENSING` | `false` | 会员取珠码已受理，设备正在出珠 | 展示出珠中并轮询 |
| `COMPLETED` | `true` | 已全量出珠并完成账户确认 | 展示成功 |
| `PARTIAL` | `true` | 实际或人工确认数量少于应出数量 | 展示异常并引导联系工作人员 |
| `FAILED` | `true` | 未完成取珠 | 展示失败并引导稍后重试或联系工作人员 |
| `CANCELED` | `true` | 操作已取消 | 退出当前取珠页 |
| `REVIEWING` | `true` | 设备结果或跨服务确认结果不明确 | 结束顾客侧流程并引导联系工作人员 |

这里的 `terminal=true` 表示当前设备屏交互已经结束，不代表后台人工结算不再更新业务结果。APP 不得因为扫码成功或收到创建响应就自行驱动硬件；出珠仍由后端通过 MQTT 下发并以设备回执为准。

## 8. 平台套餐核销状态

`redemptionStatus` 使用与会员取珠相同的 `DISPENSING`、`COMPLETED`、`PARTIAL`、`FAILED`、`CANCELED` 和 `REVIEWING` 状态语义。六位码只作为 Order 凭证预览和预占输入；设备屏不能自行判定凭证有效、已核销或可退款，也不能绕过后端操作单直接触发出珠。

## 9. 支付配置模型与部署

`tenant_payment_config.pay_provider` 表达支付提供方，使用 `WECHAT` 或 `ALIPAY`。当前微信优先方案应同时启用 `WECHAT + DEVICE_SCAN` 和 `WECHAT + MINIAPP`，并绑定同一个微信支付账户。支付账户的 `appId` 使用已关联当前商户号的会员小程序 AppId；微信 Native 不需要公众号 AppSecret。关闭支付宝时，不启用 `ALIPAY + DEVICE_SCAN` 绑定。

服务端选路顺序为：公众号或支付宝聚合入口存在时保持聚合扫码；两者均不可用且 `WECHAT + DEVICE_SCAN` 完整时直接创建 `WECHAT_NATIVE`；Native 不可用时使用 `WECHAT + MINIAPP` URL Link 兜底。Native 直付的订单与支付流水渠道为 `WECHAT_NATIVE`，小程序兜底的最终渠道为 `WECHAT_JSAPI`。

会员小程序 URL Link 由 Store 服务使用 `pinball.store.miniapp.wechat.app-id` 和 `app-secret` 生成，这组配置必须对应同一个已发布的会员小程序。缺少该配置时，仅小程序租户无法创建设备支付二维码；如果同时存在公众号或支付宝入口，服务端会自动回退到现有聚合扫码地址。

上线前执行：

`sql/payment_wechat_provider_native_20260728.sql`

`sql/payment_aggregate_scan_alipay_phase2_20260730.sql`

该迁移会把现有 `WECHAT_JSAPI` 商户配置转为 `WECHAT`。新旧 payment 服务不能同时使用这份配置，需在维护窗口内执行迁移并紧接着部署新版本。

需要部署：`gateway`、`device`、`store`、`order`、`payment`，并同步发布会员小程序入口路由更新。

## 10. 下一阶段

Android 原生 Kotlin 设备 APP 暂不在当前工作范围。会员存珠设备屏提示需求已经完成审计：当前设备入口场景码按设备稳定复用，设备 APP 没有某次会员存珠的可信会话键，因此不新增“按设备查询最新存珠”的接口；会员小程序继续按业务单 ID 轮询并展示结果。未来若要求设备屏同步展示存珠状态，必须先引入一次性屏幕会话并与会员创建的存珠操作绑定。

设备 APP 运维能力复用审计也已完成：APP 版本台账复用 MQTT `report/status`，APK 远程升级复用 `moduleType=apk` 的升级任务和 `upgrade-progress` 回执，APP 脱敏日志复用 `collect_log` 与签名文件上传，支付状态复用 `bootstrap.features`，扫码器、屏幕和本地服务异常复用统一 `report/fault`。无操作超时、防烧屏和组件正常态自检属于 APP 本地职责。当前后端未定义独立最低版本策略，也未提供可续传日志分片协议；只有产品确认策略作用域或真机证明单文件上传不能满足弱网需求后，才分别设计，不能从历史升级包或多个独立文件自动推导。故障页已经可以展示 `deviceNo`，客服电话使用门店联系电话还是平台客服电话仍需产品确认，因此暂不增加字段。

美团、抖音、快手等第三方团购核销放在后续阶段；渠道、验券、撤销和退款合同明确前，入口继续保持不可用。设备侧路由码约定见《第三方平台核销接入设计》15.3 节：`MT:`、`DY:`、`KS:` 仅是本系统路由前缀，不是第三方官方原始码格式。
