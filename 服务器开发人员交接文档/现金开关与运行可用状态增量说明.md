# 现金开关与运行可用状态增量说明

> 文档状态：开发联调基线  
> 更新日期：2026-08-01  
> 适用对象：售珠机 Android APP、设备主板适配、后端联调与测试人员

## 1. 本次说明解决什么问题

设备 APP 同时会接触两个看起来都像“现金是否开启”的字段：

- MQTT `sync_cash_configuration.data.cashAcceptanceEnabled`
- HTTP bootstrap `cashSale.available`

它们不是同一个开关，不能互相替代。

```text
cashAcceptanceEnabled = 商家配置上是否允许设备接收现金
cashSale.available     = 当前这一刻是否允许用户操作现金购珠
```

设备离线、忙碌或配置版本未完成应用时，可能出现：

```text
cashAcceptanceEnabled = true
cashSale.available = false
```

这是合法状态，不表示商家关闭了现金功能。

## 2. 字段职责矩阵

| 字段 | 来源 | 持久化 | 控制对象 | 能否表示商家开关 |
| --- | --- | --- | --- | --- |
| `cashAcceptanceEnabled` | MQTT `sync_cash_configuration` | 必须 | 版本化现金配置和验钞器配置开关 | 是 |
| `configVersion` | MQTT `sync_cash_configuration` | 必须 | 当前完整现金配置版本 | 否 |
| `cashSaleItems` | MQTT `sync_cash_configuration` | 必须完整持久化 | 面额、介质、档位和出珠数量映射 | 否 |
| `cashSale.available` | HTTP bootstrap | 不作为配置持久化 | 当前现金购珠入口和运行门控 | 否 |
| `cashSale.unavailableReason` | HTTP bootstrap | 不需要 | 当前禁用原因展示和排查 | 否 |
| `cashSale.configurationVersion` | HTTP bootstrap | 可用于核对 | 服务端确认设备已经应用的版本 | 否 |
| `cashSale.tiers` | HTTP bootstrap | 不覆盖 MQTT 本地配置 | 已应用快照展示与核对 | 否 |
| `features[CASH_PURCHASE].available` | HTTP bootstrap | 不需要 | 首页现金购珠功能入口 | 否 |

`cashSale.available` 与 `features[code=CASH_PURCHASE].available` 的运行结果一致。设备首页优先按
`features` 渲染入口，现金业务页可以读取 `cashSale` 的版本、档位和不可用原因。

## 3. 服务端如何计算 `cashSale.available`

服务端按顺序检查：

1. 设备是否获得 `DIRECT_PURCHASE` 直接购珠授权；
2. 数据库现金配置 `cash_acceptance_enabled` 是否为开启；
3. 服务端发布版本 `configuration_version` 是否大于 0；
4. 设备回执版本 `applied_configuration_version` 是否与发布版本完全相等；
5. 对应已应用版本是否存在不可变现金配置快照；
6. 设备 MQTT 通信状态是否在线；
7. 设备运行状态是否为空闲；
8. Account 域门店可用物料库存是否足以覆盖已应用档位中的最大出珠数量。

只有全部满足时返回：

```json
{
  "available": true,
  "unavailableReason": null
}
```

任一条件不满足都会返回 `available=false`，并返回最先命中的 `unavailableReason`。

库存检查采用最大档位。例如当前开放 `5元 -> 5珠` 和 `10元 -> 20珠`，则 bootstrap 请求 Account 域
判断可用库存是否至少为 20 珠。库存未初始化、库存不足或库存服务不可用时均故障关闭。该查询不会
冻结库存；现金真正进入钱箱后，服务端仍会原子预占库存，因此设备不能长期缓存一次
`available=true` 作为库存保证。

## 4. 为什么离线时仍可能返回版本和档位

设备已经成功应用版本 3 后，服务端会保存：

```text
configuration_version = 3
applied_configuration_version = 3
```

如果随后 MQTT 断开，配置事实没有消失，只是运行条件不满足。因此 bootstrap 可以返回：

```json
{
  "cashSale": {
    "available": false,
    "unavailableReason": "设备通信离线",
    "configurationVersion": 3,
    "itemName": "弹珠",
    "unitName": "珠",
    "tiers": [
      {
        "cashMediumCode": "banknote",
        "denominationAmount": 500,
        "marbleQuantity": 5,
        "tierNo": "MCST..."
      }
    ]
  }
}
```

设备必须解释为：

```text
版本 3 已经应用，但当前通信离线，所以暂停现金购珠。
```

不得解释为：

```text
商家关闭了现金功能。
```

## 5. MQTT 现金配置处理要求

平台通过设备专属 `command/config` Topic 下发：

```json
{
  "messageId": "msg-cash-config-001",
  "deviceNo": "VM...",
  "commandType": "sync_cash_configuration",
  "timestamp": 1785542400000,
  "data": {
    "configVersion": 3,
    "cashAcceptanceEnabled": true,
    "changeEnabled": false,
    "cashSaleItems": [
      {
        "cashMediumType": "banknote",
        "denominationAmount": 500,
        "marbleQuantity": 5,
        "cashSaleTierNo": "MCST..."
      }
    ]
  }
}
```

推荐处理顺序：

```java
DeviceMqttCommand<?> command = codec.decode(
        topic, payload, deviceNo, System.currentTimeMillis());
CashConfigurationCommandData data =
        command.requireData(CashConfigurationCommandData.class);

if (!data.isCashAcceptanceEnabled()) {
    cashConfigurationStore.saveDisabled(data.getConfigVersion());
    cashConfigurationAdapter.disableCashAcceptance();
    publishSuccessResult(command, data.getConfigVersion());
    return;
}

List<CashTier> tiers = validateAndMapAllItems(data.getCashSaleItems());
cashConfigurationStore.saveEnabledAtomically(
        data.getConfigVersion(), data.getCashSaleItems());
CashConfigurationResult applyResult =
        cashConfigurationAdapter.apply(data.getConfigVersion(), tiers);
if (!applyResult.isApplied()) {
    cashConfigurationAdapter.disableCashAcceptance();
    publishFailedResult(command, data.getConfigVersion(), applyResult.getMessage());
    return;
}
publishSuccessResult(command, data.getConfigVersion());
```

以上存储、映射和回执辅助方法由 Android APP 实现。SDK 负责强类型解码和字段校验，不替代 Room、
SQLite、AndroidKeyStore 或主板驱动。

### 5.1 禁用配置

`cashAcceptanceEnabled=false` 时：

1. `cashSaleItems` 应为空；
2. 设备保存禁用版本；
3. 立即关闭验钞器；
4. 成功完成以上动作后回 `success + configVersion`；
5. 不得继续使用旧版本接收现金。

### 5.2 启用配置

`cashAcceptanceEnabled=true` 时：

1. 至少存在一个有效档位；
2. 所有面额使用整数分；
3. `cashMediumType` 只能是 `banknote` 或 `coin`；
4. `cashSaleTierNo` 不能重复；
5. 必须原子保存完整版本，不能混合新旧档位；
6. 硬件应用成功后才能回 `success`；
7. 任一步失败都关闭验钞器并回 `failed`。

## 6. 本地持久化最低要求

设备本地至少保存：

```text
configVersion
cashAcceptanceEnabled
changeEnabled
cashSaleItems 全量内容
sourceMessageId
applyStatus
applyTime
success/failed 终态回执
```

建议以 `configVersion` 为不可变版本主键，另维护一个“最近成功应用版本”指针。新版本写入、字段校验、
硬件应用和当前指针切换必须有明确顺序，不能覆盖唯一一份可审计记录。

进程重启时：

1. 读取最近成功应用版本；
2. 校验版本和档位完整性；
3. 若本地记录为禁用，保持验钞器关闭；
4. 若本地记录为启用，恢复档位并应用硬件；
5. 恢复失败时关闭验钞器，等待平台重新下发；
6. 不得用 bootstrap 的 `available` 生成或修改本地配置版本。

## 7. bootstrap 的正确使用方式

配置快照读取和当前入口判断必须分开：

```java
DeviceAppBootstrapResult.CashSaleInfo cashSale = home.getCashSale();

boolean hasAppliedSnapshot = cashSale != null
        && cashSale.getConfigurationVersion() != null
        && !cashSale.getTiers().isEmpty();
if (hasAppliedSnapshot) {
    renderAppliedCashTiers(cashSale.getTiers());
}

boolean entryAvailable = cashSale != null && cashSale.isAvailable();
setCashPurchaseEntryEnabled(entryAvailable);
if (!entryAvailable) {
    showCashUnavailableReason(cashSale == null
            ? "现金购珠配置不可用"
            : cashSale.getUnavailableReason());
}
```

禁止以下写法：

```java
// 错误：available 不是商家配置开关。
cashConfigurationStore.setCashAcceptanceEnabled(cashSale.isAvailable());

// 错误：离线或忙碌时会丢失仍然有效的已应用快照展示。
if (cashSale.isAvailable()) {
    saveCashConfigurationFromBootstrap(cashSale);
}

// 错误：忽略 unavailableReason，统一显示为商家关闭。
if (!cashSale.isAvailable()) {
    showMessage("商家未开启现金");
}
```

## 8. 启动和恢复顺序

设备日常启动顺序：

```text
读取设备身份和 MQTT 凭证
-> 调用 reactivate 更新 Broker、Topic 和心跳参数
-> 原子保存新凭证
-> 连接 MQTT
-> 订阅 command/#
-> 发布 heartbeat
-> 发布 status
-> 恢复本地成功应用的现金配置
-> 恢复未确认现金事件和命令终态
-> 请求 bootstrap
-> 按 cashSale.available 开放或禁用当前现金入口
```

不要在 MQTT 尚未连接、心跳尚未上报时，把第一次 bootstrap 的“设备通信离线”当作最终配置状态。
MQTT 连接成功并完成首次心跳、状态上报后，应重新请求 bootstrap。

MQTT 会话断开时，设备应立即暂停现金接收和现金入口。重连后先恢复订阅、心跳、状态和待确认消息，
再刷新 bootstrap；不能沿用断线前的 `available=true`。

## 9. 典型状态与设备行为

| 场景 | MQTT 本地配置 | bootstrap | 设备行为 |
| --- | --- | --- | --- |
| 商家关闭现金 | `cashAcceptanceEnabled=false` | `available=false` | 持久化禁用，关闭验钞器和入口 |
| 商家开启但设备未应用 | 旧版本或无版本 | `available=false`，提示配置未应用 | 关闭验钞器，等待新配置 |
| 配置已应用但 MQTT 离线 | 已启用完整版本 | `available=false`，提示通信离线 | 暂停入口和收现，保留本地配置 |
| 配置已应用但设备忙碌 | 已启用完整版本 | `available=false`，提示当前状态 | 暂停入口和收现，操作结束后刷新 |
| 配置已应用但库存不足 | 已启用完整版本 | `available=false`，提示库存不足 | 暂停入口和收现，保留本地配置，后续刷新 |
| 库存服务暂不可用 | 已启用完整版本 | `available=false`，提示查询不可用 | 故障关闭，不按旧可用状态继续收现 |
| 配置已应用且在线空闲 | 已启用完整版本 | `available=true` | 允许现金入口，按已应用档位工作 |
| 本地配置损坏 | 不可信 | 即使曾返回可用也不能依赖 | 关闭验钞器，等待重新下发 |
| bootstrap 请求失败 | 已应用版本仍可审计 | 无最新运行状态 | 保守暂停入口，不自行猜测可用 |

## 10. 不可用原因展示

APP 应直接展示服务端 `unavailableReason`，常见值包括：

| 原因 | 含义 |
| --- | --- |
| `设备未获得直接购珠授权` | 授权条件不满足，不代表现金配置表开关一定关闭 |
| `设备未开启现金接收` | 商家现金配置开关未开启或没有配置 |
| `现金配置尚未被设备确认应用` | 发布版本与设备回执版本不一致 |
| `设备已应用的现金配置快照不存在` | 服务端配置数据异常，禁止营业 |
| `设备通信离线` | MQTT 在线状态不满足，保留配置但暂停营业 |
| `设备当前处于...` | 设备不是空闲状态，暂停营业 |
| `门店物料库存尚未初始化` | Account 域尚无该门店物料库存账，禁止收现 |
| `门店可用物料库存不足` | 库存不足以覆盖当前最大现金档位，暂停收现 |
| `门店物料库存查询暂不可用` | Account 域查询异常，按故障关闭处理 |

不得把所有原因改写成“现金关闭”。运维排查依赖这些具体原因。

## 11. 联调检查清单

### 11.1 配置开关

- 商家关闭现金后，设备收到 `cashAcceptanceEnabled=false` 并关闭验钞器。
- 商家开启现金后，设备收到完整档位并保存相同 `configVersion`。
- 设备只有在硬件应用成功后才回 `success`。
- 重复 `messageId` 不重复应用硬件，只重发保存的终态。

### 11.2 版本一致性

- `configurationVersion == appliedConfigurationVersion` 时才可能开放入口。
- 发布新版本但设备未回执时，bootstrap 返回不可用。
- 旧版本现金事件延迟上报时仍能命中旧的不可变快照。
- 设备现金事件的 `configVersion`、介质、面额和 `cashSaleTierNo` 来自同一版本。

### 11.3 在线状态

- MQTT 未连接时 bootstrap 返回“设备通信离线”。
- 首次 heartbeat 和 status 被平台处理后，重新请求 bootstrap。
- MQTT 断开时立即暂停现金接收。
- 重连后不使用旧 `available=true`，必须刷新 bootstrap。

### 11.4 进程重启

- 重启后能读取最近成功应用的完整现金配置。
- 本地记录缺字段时默认关闭验钞器。
- 未确认现金事件、ACK 和终态能够继续重发。
- 重启不会生成新的 `eventNo` 或重复出珠。

### 11.5 库存门控

- 最大出珠档位为 20 珠时，库存 20 珠可用，库存 19 珠不可用。
- 库存不足时仍返回已应用 `configurationVersion` 和 `tiers`，仅入口不可用。
- 库存恢复后重新请求 bootstrap，可以恢复 `available=true`。
- Account 域超时、失败或返回不完整结果时必须为 `available=false`。
- 即使 bootstrap 返回可用，收现后的库存预占失败仍按服务端异常闭环处理，设备不得自行继续出珠。

## 12. 服务端配置自动重算已完成

2026-08-01 服务端已经完成以下安全和一致性闭环：

1. bootstrap 只有发布版本与应用版本相等时才允许现金购珠；
2. bootstrap 通过 Account 域只读接口按最大现金档位检查库存；
3. 库存未初始化、不足或查询异常时故障关闭；
4. 收现后的原子库存预占继续作为最终权威校验；
5. 现金规则、档位和直接购珠授权变化后自动重算相关设备配置；
6. 消息丢失、服务重启、授权到期和授权未来生效由 Device 定时扫描补偿；
7. 等价有效载荷不递增版本，变化或失败退避到期后才重新发布。

这不改变设备字段职责。MQTT 配置仍是设备本地配置的唯一来源，bootstrap 仍只表达当前运行可用状态。

## 13. 哪些变化会触发新配置

以下 Product 规则变化在数据库事务提交后通知 Device：

- 创建现金规则；
- 替换现金档位；
- 启用或停用现金规则；
- 删除已经停用的现金规则。

以下 Device 授权变化在数据库事务提交后进入设备重算队列：

- 单台设备授予、挂起或恢复 `DIRECT_PURCHASE`；
- 批量修改多台设备的 `DIRECT_PURCHASE`；
- 设备生命周期变化导致全部业务授权挂起。

此外，Device 每 10 秒执行一轮补偿工作，默认每轮扫描 100 条商家已开启现金接收的配置。游标扫到末尾
后从头开始，因此以下没有明确数据库写操作的时间变化也会最终生效：

- 授权到达 `effectiveTime`；
- 授权到达 `expireTime`；
- Product 或 RocketMQ 暂时不可用后恢复；
- 服务实例在事务提交和消息发送之间退出；
- MQ 消息重复、延迟或丢失。

消息负责低延迟，扫描负责最终收敛。设备不能假设“没有立即收到 MQTT 指令”就代表规则没有变化。

## 14. 服务端如何计算有效配置

每台设备的有效现金配置是以下四个条件的交集：

```text
商家现金接收开关已开启
AND DIRECT_PURCHASE 当前处于有效授权时间窗口
AND 门店物料存在当前启用的现金规则和档位
AND 设备该现金介质和面额已启用
```

举例：

```text
设备启用面额：纸币 5 元、纸币 10 元、硬币 1 元
门店当前档位：5 元 -> 50 珠、10 元 -> 120 珠、20 元 -> 260 珠

最终下发：
纸币 5 元 -> 50 珠
纸币 10 元 -> 120 珠

不会下发：
硬币 1 元，因为 Product 没有 1 元档位
20 元，因为设备没有启用 20 元面额
```

只要交集仍非空，部分档位失效不会关闭全部现金能力，而是发布仅包含有效交集的新完整版本。交集为空、
规则停用或授权失效时，发布禁用版本。

## 15. 自动关闭与恢复时序

### 15.1 授权撤销或规则停用

```text
商家提交变化
-> 数据库事务提交
-> Device 定向重算，或稍后由全量扫描发现
-> configuration_version 递增
-> 创建 cashAcceptanceEnabled=false 的 MQTT 配置命令
-> bootstrap 因发布版本与应用版本不一致返回 available=false
-> 设备收到指令，保存禁用版本并关闭验钞器
-> 设备回 success + configVersion
-> 服务端记录 applied_configuration_version
-> bootstrap 继续 available=false，原因由当前授权或配置状态决定
```

禁用载荷固定为：

```json
{
  "configVersion": 4,
  "cashAcceptanceEnabled": false,
  "changeEnabled": false,
  "cashSaleItems": []
}
```

### 15.2 授权或规则恢复

```text
商家恢复授权或规则
-> 服务端重新计算当前有效交集
-> 发布更高 configVersion 的完整启用配置
-> 在设备回执前 bootstrap 保持 available=false
-> 设备原子保存并应用新版本
-> 设备回 success + configVersion
-> 版本一致且在线、空闲、库存充足时 bootstrap 才返回 available=true
```

设备不得在授权恢复时直接恢复历史启用版本。历史档位可能已经变化，必须等待新的完整启用版本。

## 16. 幂等、并发与失败补偿

服务端比较最近一次已发布 MQTT 载荷时忽略 `configVersion`，只比较：

```text
cashAcceptanceEnabled
changeEnabled
排序后的 cashSaleItems
```

因此重复 MQ 消息、重复扫描或多实例同时重算不会因为触发次数增加而不断生成新版本。真正发布时，服务端
使用配置记录的乐观锁同时校验实体版本和当前配置版本；只有一个实例能递增版本、写不可变快照并创建
设备命令。

最新配置命令仍为待发送时，新版本会把旧待发送命令标记为已覆盖。已经发送、成功、失败或取消的历史
命令不会删除，继续作为审计记录。设备始终以收到的更高 `configVersion` 为准。

相同有效载荷的最新命令失败后不会每 10 秒重复创建。默认等待 600 秒再发布一个更高版本，避免硬件故障
期间持续堆积命令。历史命令 JSON 损坏时按“不等价”处理，服务端会生成一条结构正确的新配置用于自愈。

Product 服务暂时不可用时，本轮重算失败并等待后续补偿，不会因为一次跨服务故障立刻下发关闭版本。
这是为了避免把“无法读取最新规则”错误解释为“规则不存在”。但 bootstrap 和设备本地运行门控仍按
既有规则故障关闭，设备不能因为服务端暂未下发新配置而忽略在线、版本或库存检查。

## 17. 联调新增场景

除第 11 节检查项外，本次必须增加以下联调：

1. 启用配置已经应用后停用现金规则，确认收到更高版本禁用配置并关闭验钞器；
2. 恢复规则后确认收到更高版本完整启用配置，回执前 bootstrap 不开放；
3. 撤销 `DIRECT_PURCHASE` 后确认禁用，恢复后确认重新启用；
4. 设置一分钟后生效的授权，确认到时无需再次操作即可收到启用版本；
5. 设置一分钟后到期的授权，确认到时无需再次操作即可收到禁用版本；
6. 删除一个现金档位，确认新版本只保留剩余有效交集；
7. 连续保存相同规则，确认没有无意义的 `configVersion` 连续增长；
8. 让设备对配置回 `failed`，确认退避期内不堆积新命令，退避到期后收到新版本；
9. 暂停 RocketMQ 后修改规则，确认 Device 全量扫描最终仍能下发；
10. 多实例同时运行扫描，确认每次有效变化只形成一个成功发布版本。

联调时至少记录：

```text
deviceNo
商家现金开关
DIRECT_PURCHASE 状态及生效/失效时间
Product 规则版本和档位
设备启用介质与面额
configuration_version
applied_configuration_version
device_command.biz_version/status/result_message
设备本地 configVersion/applyStatus
bootstrap cashSale.available/unavailableReason
```

排查顺序应从服务端有效配置交集开始，再看命令、设备应用回执和 bootstrap 运行门控。不要只看
`cashSale.available=false` 就判断商家开关未开启。

## 18. 部署前提

本次服务端自动重算不新增数据库表，也没有需要设备侧执行的 SQL。后端新增 RocketMQ Topic
`pxd_product`，规则变化 Tag 为 `marble_cash_sale_rule_changed`，Device 消费组为
`GID_device_cash_rule_changed`。如果生产 Broker 禁止自动创建 Topic，后端运维必须提前创建 Topic。

MQ 不可用时规则保存仍会成功，Device 定时扫描会最终补偿，但新配置下发会从秒级退化为扫描周期加上
全量配置轮转时间。MQ 恢复后不需要设备清缓存或重装 APP。
