# 现金投币与出珠增量说明

本文供售珠机 Android APP 和主板驱动开发同事使用，说明现金进入设备后，平台与设备如何
共同完成一次出珠。本文只描述当前协议：一次只接收一张纸币或一枚硬币，`cashCount=1`，
不支持多枚累计支付和找零。

## 1. 数量由谁决定

出珠数量由平台决定，设备负责执行和真实计数。

1. 平台通过 `sync_cash_configuration` 下发每个现金档位的
   `denominationAmount -> marbleQuantity` 配置。
2. 设备识别现金后，只按已经持久化并生效的配置上报现金事件。
3. 平台校验配置快照并创建订单，再下发 `dispense_marbles.quantity`。
4. 设备只能按 `dispense_marbles.quantity` 驱动硬件，完成后上报真实
   `actualQuantity`。

`marbleQuantity` 用于确认当前现金属于哪个平台档位，不能在验钞器收款后直接驱动电机；
`cash_event_response.requestedQuantity` 也只用于展示平台处理状态，不能驱动电机。

## 2. 完整时序

```text
平台下发 sync_cash_configuration
-> 设备完整校验、持久化并应用配置
-> 设备上报配置 ACK/终态
-> 应用成功后才开启验钞器
-> 验钞器确认一张纸币或一枚硬币已经不可逆进入钱箱
-> 设备持久化 accepted 事件和稳定的 eventNo
-> 设备发布 report/cash-event
-> 平台下发 cash_event_response
-> 设备等待与该事件关联的 dispense_marbles
-> 设备校验并持久化 messageId 和完整指令
-> 设备发布出珠 ACK
-> 设备调用 MarbleHardwareAdapter.dispense
-> 设备发布包含真实 actualQuantity 的出珠终态
-> 平台下发 command_result_ack
-> 设备确认后删除对应 outbox 消息
```

收到 `cash_event_response` 不代表可以出珠。只有通过 SDK 协议层校验的
`dispense_marbles` 才是物理出珠授权。

## 3. 现金配置

平台通过本机 `command/config` Topic 下发 `sync_cash_configuration`。设备使用
`CashConfigurationCommandData` 读取：

- `configVersion`：本次完整配置版本；
- `cashAcceptanceEnabled`：是否允许接收现金；
- `changeEnabled`：当前是否允许找零，现阶段应为 `false`；
- `cashSaleItems[].cashMediumType`：`banknote` 或 `coin`；
- `cashSaleItems[].denominationAmount`：面额，单位为分；
- `cashSaleItems[].marbleQuantity`：平台配置的珠数；
- `cashSaleItems[].cashSaleTierNo`：现金档位编号。

APP 必须把完整版本交给 `CashConfigurationAdapter.apply`。只有配置完整持久化且硬件应用成功，
才能开启验钞器。配置被禁用、校验失败或应用失败时，调用
`CashConfigurationAdapter.disableCashAcceptance()`。

处理逻辑必须明确分支，不能使用 `bootstrap.cashSale.available` 代替
`cashAcceptanceEnabled`：

```java
CashConfigurationCommandData data =
        command.requireData(CashConfigurationCommandData.class);
if (!data.isCashAcceptanceEnabled()) {
    // 先持久化“该版本已禁用”，再关闭现金器并回成功终态。
    cashConfigurationStore.saveDisabled(data.getConfigVersion());
    cashConfigurationAdapter.disableCashAcceptance();
} else {
    // 先原子持久化完整版本和全部档位，再应用到硬件。
    cashConfigurationStore.saveEnabled(
            data.getConfigVersion(), data.getCashSaleItems());
    CashConfigurationResult result = cashConfigurationAdapter.apply(
            data.getConfigVersion(), toCashTiers(data.getCashSaleItems()));
    if (!result.isApplied()) {
        cashConfigurationAdapter.disableCashAcceptance();
        // 回 failed，不能回 success。
    }
}
```

以上 `cashConfigurationStore` 和 `toCashTiers` 由 Android APP 实现，SDK 不提供 Android 数据库。
设备进程重启后必须先从本地数据库恢复最近成功应用的完整配置；数据缺失、版本不完整或校验失败时
默认关闭现金器，等待平台重新下发配置。

`bootstrap.cashSale.available` 表示当前是否允许用户操作现金购珠入口。它会受到设备在线、空闲、
授权、配置版本一致性和门店物料库存影响。该值为 `false` 时应立即关闭当前现金入口并按
`unavailableReason` 展示原因，但不能据此把本地持久化的商家开关改成关闭，也不能删除已应用档位。

## 4. 上报现金事件

现金已经不可逆进入钱箱后，设备向激活响应指定的现金事件 Topic 发布 QoS 1 消息：

```json
{
  "eventNo": "CE-A-20260801-000001",
  "eventType": "accepted",
  "cashMediumType": "banknote",
  "denominationAmount": 500,
  "cashCount": 1,
  "cashSaleTierNo": "MCST202607280001",
  "configVersion": 12,
  "timestamp": 1785542400000
}
```

`cashMediumType`、`denominationAmount`、`cashSaleTierNo` 和 `configVersion` 必须来自收款时
已经应用的同一份配置快照。同一笔物理现金事件永久复用同一个 `eventNo` 和完全相同的
payload；超时、断网和重连只能重发，不能生成新事件。

## 5. 处理平台响应

`DeviceMqttCommandCodec.decode` 会把平台响应解析为
`CashEventResponseCommandData`。各状态处理如下：

| `status` | 设备处理 |
| --- | --- |
| `pending` | 平台已持久化现金事件，等待创建订单，继续等待后续响应或 `dispense_marbles` |
| `processing` | 平台正在处理，继续等待 `dispense_marbles` |
| `completed` | 事件已经完成，不得补做本地出珠 |
| `manual_review` | 关闭现金接收，等待人工核实 |
| `rejected` | 不得出珠，按平台提示进入异常处理 |
| `unknown` | 使用原 `eventNo` 重发原现金事件，不得自行出珠或退款 |

使用 `isPending/isProcessing/isCompleted/isManualReview/isRejected/isUnknown` 判断状态，不要
在 APP 中另写状态枚举。除 `unknown` 外，响应表示平台已经明确处理原现金事件，可以使用
`CashEventResponseCommandData.getReceiptKey()` 调用 `markBusinessConfirmed`；`unknown` 必须保留
原事件并重发。任何状态下都不能使用响应中的 `requestedQuantity` 直接出珠。

## 6. 执行出珠指令

收到 `dispense_marbles` 后按以下顺序处理：

```java
DeviceMqttCommand<?> command = commandCodec.decode(
        topic, payload, deviceNo, System.currentTimeMillis());

DispenseRequest request = hardwareCommandMapper.toDispenseRequest(
        command, System.currentTimeMillis());

// 在同一事务中持久化 messageId、完整指令和“尚未启动硬件”状态。
DeviceCommandResult ack = DeviceCommandResult.acknowledgement(
        command, ackEventNo, System.currentTimeMillis());
// 编码 ACK，写入 outbox，再通过 MqttSessionManager.publishDurable 发布。

HardwareExecutionResult hardwareResult = marbleHardwareAdapter.dispense(request);
DeviceCommandResult terminal = hardwareCommandMapper.toTerminalResult(
        command, terminalEventNo, hardwareResult, System.currentTimeMillis());
// 编码终态，写入 outbox，再通过 MqttSessionManager.publishDurable 发布。
```

`DeviceMqttCommandCodec` 和 `DeviceHardwareCommandMapper` 会校验本机 Topic、`deviceNo`、命令
类型、`quantity`、`operationNo`、`operationToken` 和过期时间。APP 仍须在本地数据库按
`messageId` 做持久化幂等：重复指令只重发已保存的 ACK/终态，绝不能再次启动电机。

ACK 只表示设备已经可靠接单，不表示已经出珠。`MarbleHardwareAdapter.dispense` 返回的
`HardwareExecutionResult.actualQuantity` 必须是真实物理计数，范围为 `0..quantity`。
全量、部分和零出珠都按真实结果上报；物理结果无法确认时保留 ACK 并转人工处理，不能伪造
`actualQuantity=0` 的终态。

## 7. 断网与进程恢复

设备本地至少持久化以下内容：

- 已应用的现金配置版本和完整档位；
- 未被平台确认的现金事件 `eventNo` 和原始 payload；
- 出珠指令的 `messageId`、`operationNo`、`operationToken` 和原始 payload；
- 硬件是否已经启动、真实 `actualQuantity`、ACK 和终态 payload；
- `PendingMessageStore` 中等待平台业务确认的 outbox 消息。

重连后先订阅命令 Topic，再重发未确认的现金事件和 ACK/终态。MQTT PUBACK 只表示 Broker
收到消息，不能删除业务 outbox；只有收到平台 `command_result_ack` 后，才能调用
`markBusinessConfirmed`。任何恢复路径都不能重复执行已经启动过的物理动作。

## 8. 禁止行为

- 根据本地 `marbleQuantity` 或 `cash_event_response.requestedQuantity` 直接出珠；
- 离线收款后自行出珠，或在未收到 `dispense_marbles` 时出珠；
- 相同 `messageId` 重复驱动电机；
- 将 ACK 当作出珠成功；
- 现金事件重试时更换 `eventNo` 或修改 payload；
- 物理结果未知时伪造 `actualQuantity=0`；
- 在日志中输出 MQTT 密码、设备令牌或 `operationToken`。

## 9. 联调验收

至少覆盖：配置启用/禁用、未应用配置时验钞器关闭、每个面额对应的出珠数量、现金事件重发、
重复 `messageId`、全量/部分/零出珠、断网重连、APP 进程重启、指令过期、平台业务确认以及
物理结果未知转人工。所有场景都要核对电机实际启动次数和平台记录的 `actualQuantity`。
