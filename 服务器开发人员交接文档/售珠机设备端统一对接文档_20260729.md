# 售珠机设备端统一对接文档

> 版本：2026-07-29
>
> 生产网关：`https://api.dzxd.top`
>
> MQTT Broker、账号、密码和 Topic 以设备激活接口返回值为准

> 当前项目仍处于开发联调阶段，尚未上线且没有生产存量数据。本轮允许破坏性重置：不兼容、不迁移、不读取历史测试私钥、历史 MQTT 凭证、旧包名数据或旧应用数据库，也不需要编写旧版本回退逻辑。设备端 AI 应直接按本文实现当前最终协议。

## 1. 阅读说明

这是提供给售珠机设备同事的唯一主对接文档，覆盖设备认证、MQTT 连接、状态上报、出珠、收珠、现金和基础运维协议。

设备同事不需要同时阅读仓库里的认证设计、旧流程迁移、现金长期方案、后端状态机设计和历史联调记录。那些文档只用于后端追溯；如果内容冲突，以本文和当前服务端代码为准。

本文的“设备端”指售珠机硬件控制程序及其本地服务，不包含设备屏 Android 原生 Kotlin APP。设备屏 APP 的 HTTP 页面、二维码和交互按[《售珠机设备屏 APP 接口协议》](售珠机设备屏APP接口协议_20260728.md)对接；无论业务由套餐核销、会员取珠、微信支付还是现金触发，硬件最终只执行本文定义的 MQTT 指令。

## 2. 设备端需要实现什么

设备程序只需要稳定实现以下职责：

1. 安全保存单设备身份私钥和 MQTT 凭证。
2. 完成后续激活、MQTT 登录、订阅、心跳和状态上报。
3. 只处理发往本机 `deviceNo` 的合法指令。
4. 固定数量出珠只执行 `dispense_marbles`。
5. 会员开放式收珠只执行 `collect_marbles`。
6. 现金不可逆进入钱箱后上报 `cash-event`，但不能自行决定价格或出珠。
7. 持久化指令、物理动作和终态，抵抗重复投递、断网和重启。
8. 上报故障、升级进度和异步任务结果，日志必须脱敏。

设备程序不负责订单、支付、会员账户、套餐凭证、库存和退款决策，也不得根据页面提示、支付页面、核销响应或现金面额自行启动出珠。

## 3. 设备标识和安全凭据

### 3.1 deviceNo

`deviceNo` 是 HTTP、MQTT 登录和 Topic 的通信唯一标识。平台会执行以下规范化：

```text
删除空格、冒号、短横线和下划线，再转成大写
```

设备本地应始终保存并使用规范化值。`deviceId` 是平台数据库主键，`deviceSn` 是业务资产编号，都不能替代 `deviceNo`。

### 3.2 游戏设备与售珠机如何区分

弹珠机和售珠机共用同一套身份登记、报到、激活、凭证恢复和 MQTT 认证协议，不存在“游戏设备认证接口”和“售珠机认证接口”两套入口。设备端不得在报到、激活或凭证恢复请求中自行增加或声明 `deviceType`。

平台以设备档案关联的型号作为设备类型唯一事实来源，判定链如下：

```text
deviceNo -> device_machine -> modelId -> device_model.deviceType
```

正式设备类型枚举如下：

| deviceType | 后端枚举 | 含义 |
| --- | --- | --- |
| `1` | `PINBALL_MACHINE` | 弹珠机，即游戏设备 |
| `2` | `MARBLE_VENDING_MACHINE` | 售珠机 |

身份公钥只与 `deviceNo` 绑定，不携带设备类型。设备首次报到也只建立待认领记录，不由设备决定类型；商户认领、平台建档或批量自动认领时必须选择型号，平台校验传入的 `deviceType` 与该型号的 `deviceType` 完全一致后，才写入正式设备档案。

当前联调设备 `VMIT03828355QAOC` 的档案必须关联售珠机型号，权威类型为 `deviceType=2`。如果平台档案类型错误，应由平台修正型号或认领数据，设备端不能通过修改认证 payload 纠正。

认证成功只代表身份和凭证有效。进入业务处理后，平台会再次按档案类型限制能力：弹珠机可上报游戏记录并接收游戏配置；售珠机可执行 `dispense_marbles`、`collect_marbles`、现金协议和设备屏 APP 业务。设备类型不匹配时，即使 MQTT 已连接，相应业务也会被拒绝。

### 3.3 单设备身份私钥

- 算法：ECDSA P-256 / `secp256r1`
- 签名算法：`SHA256withECDSA`
- 签名结果：ASN.1 DER 后使用无填充 Base64URL
- 每台设备必须使用独立密钥对
- 私钥不得上传、打印、截图或写入普通日志
- 密钥对必须由最终设备程序在设备本机生成；平台和后端不生成、不托管身份私钥
- 私钥必须进入设备安全存储，并能在重启及同包名覆盖升级后继续读取

身份私钥用于首次报到、首次激活和平台授权的 MQTT 凭证恢复，不用于 MQTT 登录。

### 3.4 MQTT 凭证

激活或凭证恢复成功会返回 `mqttClientId`、`mqttUsername`、`mqttPassword`、Broker 和 Topic。设备必须原子保存整组凭证，只有全部写入成功后才能替换旧值；应用升级、重启和普通业务配置清理不能删除它们。

本项目不迁移历史测试凭证，也不要求从旧包名、旧数据库或其他历史程序中查找凭证。设备同事需要在继续联调前冻结最终应用包名、签名证书和安全存储方案；从本轮重新生成身份密钥并取得新 MQTT 凭证开始，后续同包名覆盖升级必须能够继续读取。卸载应用、清除应用数据和更换签名证书不属于凭证保留场景。

已激活设备再次调用激活接口时，使用当前 `mqttPassword` 做 HMAC-SHA256：

```text
device-activation|mqtt|{deviceNo}|{nonce}|{timestamp}
```

`nonce` 长度为 16 至 64，只允许字母、数字、下划线和短横线；每次请求必须重新生成。`timestamp` 使用 Unix 毫秒时间戳，与平台误差不得超过 5 分钟。

### 3.5 公钥登记模式

设备 SDK 在首次报到时携带 X.509 SubjectPublicKeyInfo 公钥，私钥始终留在设备。后端开启
`device.identity.auto-registration-enabled` 时先验签再自动登记；关闭时由平台提前登记相同公钥。
两种模式使用同一个设备报到接口，已经登记的身份不会被请求公钥覆盖。

需要平台预登记或批量生产登记时，公钥可使用标准 Base64，或带 `PUBLIC KEY` 头尾的 PEM。

批量交付使用 UTF-8 JSON 文件，建议命名为 `device-identity-public-keys-{批次号}.json`，格式如下：

```json
{
  "devices": [
    {
      "deviceNo": "VMIT03828355QAOC",
      "publicKey": "MFkwEwYHKoZIzj0CAQYIKoZIzj0DAQcDQgAE...",
      "remark": "2026-07 联调批次"
    }
  ]
}
```

单批最多 200 台。后端使用平台权限调用 `POST /api/platform/device/identity/batch`；平台会统一规范化设备编号、校验 P-256 公钥、阻止批次内或数据库中的设备号/公钥重复，任一项失败时整批不登记。该接口不由设备直接调用。

已经存在身份记录的设备不能再次批量登记，应由平台后端调用 `PUT /api/platform/device/identity/{deviceNo}/public-key` 轮换公钥。

## 4. 认证和启动流程

### 4.1 当前联调设备一次性重置

当前联调设备 `VMIT03828355QAOC` 已完成身份登记、报到、认领和首次激活，但历史身份私钥不是最终设备程序生成和保存的凭据。因为项目尚未上线，本轮不迁移历史数据，按以下顺序一次性重置：

1. 设备程序在本机生成新的独立 P-256 密钥对，先验证私钥重启后仍可读取。
2. 设备同事只向后端交付 `deviceNo` 和新公钥。
3. 后端为该设备轮换平台公钥；设备档案、认领关系和 `deviceNo` 保持不变。
4. 后端为该设备开启一次性 MQTT 凭证恢复窗口。
5. 设备使用新身份私钥调用凭证恢复接口，原子保存平台返回的新 MQTT 凭证。
6. 设备使用新凭证连接 MQTT，并完成重启和同包名覆盖升级验证。

不要删除设备档案，不要重新报到或认领，也不要尝试读取历史测试程序的数据。

### 4.2 日常启动

完成上述一次性重置后，日常启动流程固定为：

```text
读取 deviceNo 和 MQTT 凭证
-> 使用 MQTT HMAC 调用后续激活
-> 更新 Broker、Topic 和心跳配置
-> 连接 MQTT
-> 订阅本机 command/#
-> 发布 heartbeat
-> 发布 status
-> 恢复未完成事件和未确认终态
```

### 4.3 MQTT 凭证丢失

设备不得自动降级为身份私钥直接取回密码。恢复流程必须由平台授权：

1. 平台管理员为指定 `deviceNo` 开启一次性 10 分钟恢复窗口。
2. 设备调用 `POST /api/device/credential-recovery`。
3. 签名原文为：

```text
device-credential-recovery|identity|{deviceNo}|{nonce}|{timestamp}
```

请求字段如下，每次请求都必须重新生成 `nonce`、`timestamp` 和 `signature`：

```json
{
  "deviceNo": "VMIT03828355QAOC",
  "firmwareVersion": "1.0.0",
  "apkVersion": "1.0.0",
  "nonce": "recovery7d3b18d146a9488fb23c",
  "timestamp": 1785290000000,
  "signature": "设备身份私钥生成的签名"
}
```

4. 恢复成功后旧 MQTT 凭证立即失效。
5. 设备必须先原子保存新凭证，再使用新凭证重连。
6. 同一恢复申请只能成功消费一次。

## 5. MQTT Topic

统一使用 QoS 1。设备只能发布和订阅自己的 `deviceNo`。

| 方向 | Topic | 用途 |
| --- | --- | --- |
| 设备 → 平台 | `pxd/v1/device/{deviceNo}/report/heartbeat` | 心跳 |
| 设备 → 平台 | `pxd/v1/device/{deviceNo}/report/status` | 状态、网络和版本 |
| 设备 → 平台 | `pxd/v1/device/{deviceNo}/report/fault` | 故障 |
| 设备 → 平台 | `pxd/v1/device/{deviceNo}/report/redemption-request` | 设备扫码核销请求 |
| 设备 → 平台 | `pxd/v1/device/{deviceNo}/report/cash-event` | 收现和真实退币事件 |
| 设备 → 平台 | `pxd/v1/device/{deviceNo}/report/command-result` | 指令 ACK 和终态 |
| 设备 → 平台 | `pxd/v1/device/{deviceNo}/report/upgrade-progress` | 升级进度 |
| 平台 → 设备 | `pxd/v1/device/{deviceNo}/command/control` | 核销响应、出珠、收珠、现金响应 |
| 平台 → 设备 | `pxd/v1/device/{deviceNo}/command/config` | 现金及其他配置同步 |
| 平台 → 设备 | `pxd/v1/device/{deviceNo}/command/upgrade` | 升级任务 |
| 平台 → 设备 | `pxd/v1/device/{deviceNo}/command/task` | 拉日志等异步任务 |

设备建议只订阅：

```text
pxd/v1/device/{deviceNo}/command/#
```

平台以下发 payload 中的 `deviceNo` 与本机编号一致为基本校验条件；设备上报时，平台最终以 Topic 中的 `deviceNo` 为准。

### 5.1 激活响应中的完整 mqttTopics

设备不得在代码中拼接或假定 Topic 清单，应保存并使用每次激活或凭证恢复响应返回的最新配置。本次 Device 服务版本部署后，`mqttTopics` 完整结构如下：

```json
{
  "commandSubscribeTopic": "pxd/v1/device/VMIT03828355QAOC/command/#",
  "reportTopics": {
    "heartbeat": "pxd/v1/device/VMIT03828355QAOC/report/heartbeat",
    "status": "pxd/v1/device/VMIT03828355QAOC/report/status",
    "profile": "pxd/v1/device/VMIT03828355QAOC/report/profile",
    "game-record": "pxd/v1/device/VMIT03828355QAOC/report/game-record",
    "fault": "pxd/v1/device/VMIT03828355QAOC/report/fault",
    "upgrade-progress": "pxd/v1/device/VMIT03828355QAOC/report/upgrade-progress",
    "command-result": "pxd/v1/device/VMIT03828355QAOC/report/command-result",
    "game-config": "pxd/v1/device/VMIT03828355QAOC/report/game-config",
    "redemption-request": "pxd/v1/device/VMIT03828355QAOC/report/redemption-request",
    "cash-event": "pxd/v1/device/VMIT03828355QAOC/report/cash-event"
  },
  "qos": 1
}
```

`redemption-request` 和 `cash-event` 都必须返回。若联调环境响应缺少任一项，说明 Device 服务尚未部署本次版本，先停止该项联调并通知后端，不要由设备端硬编码临时补偿。

### 5.2 通用时间和金额约定

- 所有名为 `timestamp` 的字段统一使用 Unix Epoch 毫秒时间戳，为 13 位整数，不使用秒级时间戳或格式化字符串。
- 所有名为 `expireTime` 的字段统一使用 `yyyy-MM-dd HH:mm:ss`，固定时区 `Asia/Shanghai`，精度到秒，例如 `2026-07-29 16:00:00`。该字符串不带时区后缀，设备必须按北京时间解析和比较。
- 所有名为 `denominationAmount` 的字段统一表示人民币“分”，必须是正整数。例如 `100` 表示 `1.00` 元，禁止使用元、小数或字符串。
- 设备应通过 NTP 保持系统时钟准确；无法确认时间或时钟偏差明显时，不得执行已经接近或超过 `expireTime` 的物理指令。

## 6. 心跳、状态和故障

### 6.1 心跳

设备连接成功后立即发布一次心跳，之后按激活响应中的心跳间隔发布：

```json
{}
```

平台超过约 3 分钟没有收到心跳会把设备标记为离线。

### 6.2 状态

```json
{
  "runningStatus": 0,
  "publicIp": "",
  "privateIp": "192.168.1.10",
  "networkType": "ethernet",
  "privateHttpBaseUrl": "",
  "apkVersion": "1.0.0",
  "apkVersionCode": 100,
  "firmwareVersion": "1.0.0",
  "firmwareVersionCode": 100,
  "timestamp": 1785290000000
}
```

设备启动、网络变化、版本变化和运行状态变化后应立即上报；正常在线期间可以定时补报。

`runningStatus` 是整数枚举，正式取值如下，设备不得上报表外值：

| 值 | 名称 | 含义 |
| --- | --- | --- |
| `0` | `IDLE` | 空闲，可接受正常业务指令 |
| `1` | `IN_GAME` | 游戏中 |
| `2` | `FAULT` | 故障，设备存在影响运行的异常 |
| `3` | `MAINTENANCE` | 维护中 |
| `4` | `UPGRADING` | 升级中 |

### 6.3 故障

```json
{
  "faultCode": "DISPENSER_SENSOR_ERROR",
  "faultName": "出珠计数器异常",
  "faultLevel": 3,
  "faultDesc": "连续三次未检测到出珠脉冲",
  "timestamp": 1785290000000
}
```

`faultLevel` 是整数枚举：`1=提示`、`2=一般`、`3=严重`、`4=致命`，不得上报其他值。

首版正式 `faultCode` 字典如下：

| faultCode | faultName 建议值 | 建议等级 | 适用场景 |
| --- | --- | --- | --- |
| `BALL_JAM` | 弹珠卡阻 | `3` | 弹珠通道发生卡阻 |
| `DISPENSER_SENSOR_ERROR` | 出珠传感器异常 | `3` | 出珠计数或到位信号异常 |
| `DISPENSER_MOTOR_ERROR` | 出珠电机异常 | `3` | 出珠电机无法启动、堵转或反馈异常 |
| `COLLECTOR_SENSOR_ERROR` | 收珠传感器异常 | `3` | 收珠计数或到位信号异常 |
| `COLLECTOR_MOTOR_ERROR` | 收珠机构异常 | `3` | 收珠机构无法启动、堵转或反馈异常 |
| `BANKNOTE_ACCEPTOR_ERROR` | 验钞器异常 | `3` | 验钞器离线、卡钞或状态异常 |
| `COIN_ACCEPTOR_ERROR` | 投币器异常 | `3` | 投币器离线、卡币或状态异常 |
| `SCANNER_ERROR` | 扫码器异常 | `2` | 扫码器离线或连续读取失败 |
| `DOOR_OPEN` | 设备门未关闭 | `2` | 柜门或维护门异常开启 |
| `LOCAL_STORAGE_ERROR` | 本地存储异常 | `3` | 关键状态或幂等数据无法可靠持久化 |
| `NETWORK_ERROR` | 网络异常 | `2` | 持续断网或 MQTT 无法连接 |
| `CONTROLLER_ERROR` | 主控制器异常 | `4` | 主控不可用或无法安全控制机构 |

`faultCode` 必须使用大写下划线格式且不超过 50 个字符。同设备同 `faultCode` 会归并到同一活跃故障，因此同类故障每次上报必须复用相同编码，不能拼接时间、序号或动态文本。扫码器、屏幕、本地服务、验钞器、电机和传感器异常统一走该 Topic，不为每个组件建立新协议。若硬件还有字典未覆盖的明确故障，设备同事先提交编码、中文名称、触发条件、恢复条件和建议等级，经双方确认并更新本文后再使用，不能自行动态生成新码。

## 7. 平台指令通用信封

平台指令结构统一为：

```json
{
  "messageId": "平台生成的消息号",
  "deviceNo": "设备通信编号",
  "commandType": "指令类型",
  "timestamp": 1785290000000,
  "data": {}
}
```

设备必须先校验：

1. `deviceNo` 等于本机编号。
2. `messageId` 非空且能够用于本地幂等。
3. `commandType` 是已支持的类型。
4. 指令业务字段完整，数量和有效期合法。

相同 `messageId` 重复到达时不得重复执行物理动作，只能重发已经持久化的 ACK 或终态。

设备上报的 `command-result.status` 只允许以下值：

| status | 是否终态 | 含义 |
| --- | --- | --- |
| `ack` | 否 | 设备已校验并接受指令，准备执行；不代表物理动作完成 |
| `success` | 是 | 设备已完成执行，结果字段来自真实设备状态或计数 |
| `failed` | 是 | 设备已明确执行失败，结果字段说明真实失败结果 |

同一指令的 ACK 和终态必须使用不同 `eventNo`；同一条 ACK 或终态重试必须复用原 `eventNo` 和完全相同的原始 payload。

### 7.1 command-result 业务确认

设备向 `pxd/v1/device/{deviceNo}/report/command-result` 发布 ACK 或终态后，MQTT QoS 1 的 PUBACK 只表示 Broker 已收到，不能表示平台业务已入库。平台完成业务处理后，会复用设备已经订阅的 `pxd/v1/device/{deviceNo}/command/control` 下发 `commandType=command_result_ack`：

```json
{
  "messageId": "平台新生成的确认消息号",
  "deviceNo": "VMIT03828355QAOC",
  "commandType": "command_result_ack",
  "timestamp": 1785290003000,
  "data": {
    "sourceMessageId": "msg-001",
    "eventNo": "msg-001-result",
    "commandType": "dispense_marbles",
    "resultStatus": "success",
    "receiptStatus": "recorded",
    "code": "COMMAND_RESULT_RECORDED",
    "message": "平台已持久化该指令回执",
    "retryable": false
  }
}
```

业务确认枚举和设备行为固定如下：

| receiptStatus | code | retryable | 设备行为 |
| --- | --- | --- | --- |
| `recorded` | `COMMAND_RESULT_RECORDED` | `false` | 平台已持久化该回执；设备可以删除相同 `sourceMessageId + eventNo + resultStatus` 的本地待补发记录 |
| `rejected` | `COMMAND_RESULT_NOT_RECORDED` | `true` | 平台尚未确认入库；设备保留记录，并使用相同 `eventNo` 和完全相同的原始 `command-result` payload 重试 |

平台对普通指令会核对原 `messageId`、原 `commandType`、设备和回执状态；对 `dispense_marbles`、`collect_marbles` 还会核对相同 `operationNo + eventNo` 的设备操作事件及其事件类型，全部一致后才返回 `recorded`。设备必须按 `sourceMessageId + eventNo + resultStatus` 关联确认，不能用外层确认消息的 `messageId` 替代原指令号。

`command_result_ack` 是平台业务确认通知，设备只需本地消费并清理或保留待补发记录，不得再为它上报 `command-result`，否则会形成确认循环。若业务确认丢失，设备重发原回执后平台会再次返回确认；重复收到 `recorded` 必须幂等处理。

## 8. 固定数量出珠

平台套餐核销、会员取珠、微信 Native 购珠和现金购珠最终都使用同一个 `dispense_marbles` 指令。设备不需要识别业务来源。

### 8.1 出珠指令

```json
{
  "messageId": "msg-001",
  "deviceNo": "VMIT03828355QAOC",
  "commandType": "dispense_marbles",
  "timestamp": 1785290000000,
  "data": {
    "operationNo": "O...",
    "quantity": 10,
    "operationToken": "一次性令牌",
    "expireTime": "2026-07-29 16:00:00"
  }
}
```

设备必须校验 `messageId`、`operationNo`、正整数 `quantity`、`operationToken` 和未过期的 `expireTime`。指令过期或字段不合法时禁止驱动机构。

### 8.2 ACK

设备接受指令并准备执行后立即上报 ACK。ACK 不代表已经出珠，不携带 `actualQuantity`：

```json
{
  "messageId": "msg-001",
  "commandType": "dispense_marbles",
  "status": "ack",
  "eventNo": "msg-001-ack",
  "operationNo": "O...",
  "operationToken": "原一次性令牌",
  "timestamp": 1785290000100
}
```

### 8.3 终态

```json
{
  "messageId": "msg-001",
  "commandType": "dispense_marbles",
  "status": "success",
  "eventNo": "msg-001-result",
  "operationNo": "O...",
  "actualQuantity": 10,
  "operationToken": "原一次性令牌",
  "resultCode": "DISPENSE_COMPLETED",
  "resultMessage": "出珠完成",
  "timestamp": 1785290002000
}
```

- `status` 只能是 `success` 或 `failed`。
- `actualQuantity` 必填，范围为 `0..quantity`，必须是设备真实物理计数。
- 全量、部分和零出珠都回真实数量。
- 无法确认结果时只保留 ACK，不得伪造 `actualQuantity=0`。
- ACK 和终态使用不同 `eventNo`；同一终态重传必须复用原 `eventNo`。

## 9. 设备扫码套餐核销

设备扫码或输入六位平台取珠码后发布：

```json
{
  "requestId": "scan-20260729-0001",
  "pickupCode": "123456"
}
```

同一次扫码重试必须复用原 `requestId`。平台在 `command/control` 下发 `redemption_response`：

| status | 含义 | 设备行为 |
| --- | --- | --- |
| `accepted` | 已建立确定操作 | 只展示等待提示，继续等待 `dispense_marbles` |
| `rejected` | 明确拒绝 | 展示原因，不得出珠 |
| `unknown` | 结果可能已经发生 | 停止自动重试、不得出珠，转人工核查 |

`redemption_response` 永远不能驱动出珠。核销响应和出珠指令可能乱序到达，设备只能以合法 `dispense_marbles` 为物理授权。

## 10. 会员开放式收珠

会员在小程序创建存珠业务后，平台下发：

```json
{
  "messageId": "msg-collect-001",
  "deviceNo": "VMIT03828355QAOC",
  "commandType": "collect_marbles",
  "timestamp": 1785290000000,
  "data": {
    "operationNo": "VD...",
    "maximumQuantity": 1000,
    "sessionTimeoutSeconds": 300,
    "operationToken": "一次性令牌",
    "expireTime": "2026-07-29 16:00:00"
  }
}
```

设备收到并校验指令后先 ACK，再打开收珠通道。收到指令前不得接收弹珠。达到上限、会话超时或用户在设备端确认结束后，必须关闭通道并生成唯一终态：

```json
{
  "messageId": "msg-collect-001",
  "commandType": "collect_marbles",
  "status": "success",
  "eventNo": "msg-collect-001-result",
  "operationNo": "VD...",
  "actualQuantity": 20,
  "operationToken": "原一次性令牌",
  "resultCode": "OK",
  "resultMessage": "收珠计数完成",
  "timestamp": 1785290030000
}
```

- `actualQuantity` 范围为 `0..maximumQuantity`。
- 正数 `success` 才允许平台自动入账。
- `failed` 且为 0 表示明确没有存入。
- 正数 `failed`、超时和数量越界进入人工处理。
- 设备必须持久化真实计数和终态，重启后不得生成第二个结果。

## 11. 现金直售

### 11.1 现金配置

平台通过 `command/config` 下发 `sync_cash_configuration`。核心数据包括：

```json
{
  "configVersion": 12,
  "cashAcceptanceEnabled": true,
  "changeEnabled": false,
  "cashSaleItems": [
    {
      "cashMediumType": "banknote",
      "denominationAmount": 100,
      "marbleQuantity": 10,
      "cashSaleTierNo": "MCST..."
    }
  ]
}
```

设备完整校验并持久化后，使用原 `messageId` 回 `commandType=sync_cash_configuration` 成功结果并带回 `configVersion`。未成功应用配置时必须关闭现金接收。

设备不得根据面额自行计算数量，只能使用当前已应用配置中的完整档位。

`cashAcceptanceEnabled` 是商家配置开关的权威字段。设备必须持久化该字段、`configVersion` 和完整
`cashSaleItems`，重启后从本地恢复。该字段为 `false`、本地数据不完整、版本校验失败或硬件应用
失败时必须调用 `CashConfigurationAdapter.disableCashAcceptance()`。

设备屏 bootstrap 中的 `cashSale.available` 不是同一个字段。它表示当前是否允许用户操作现金购珠，
还会受到直接购珠授权、服务端发布版本与设备应用版本是否一致、MQTT 在线状态、设备运行状态和门店
物料库存影响。
因此可能出现以下合法响应：

```json
{
  "cashSale": {
    "available": false,
    "unavailableReason": "设备通信离线",
    "configurationVersion": 3,
    "tiers": [
      {
        "cashMediumCode": "banknote",
        "denominationAmount": 500,
        "marbleQuantity": 5,
        "tierNo": "MCST..."
      }
    ]
  }
}
```

这个响应表示版本 3 的现金配置已经应用，但当前设备通信离线；不能解释为商家关闭现金。设备 APP
用 `cashSale.available` 控制当前入口，用 MQTT `cashAcceptanceEnabled` 维护配置开关，两者必须同时
满足各自职责，不能互相覆盖。

服务端按已应用档位中的最大出珠数量检查门店可用物料库存。库存不足、尚未初始化或库存服务暂不可用
时，`cashSale.available=false`，但已应用版本和档位仍可返回。该结果只控制当前入口；现金事件处理时
服务端仍执行原子库存预占，设备不得把 bootstrap 的可用结果当作长期库存承诺。

`denominationAmount` 的单位固定为人民币“分”，`100` 表示 `1.00` 元；配置、`accepted` 和 `returned` 中必须使用完全相同的整数值。设备不得上报 `1` 表示 1 元，也不得上报 `1.00` 或 `"100"`。

#### 11.1.1 规则和授权变化后的自动配置

服务端会自动处理以下变化，设备端不需要查询商家后台数据：

- 现金规则创建、档位替换、启用、停用或删除；
- 设备 `DIRECT_PURCHASE` 授权授予、挂起、恢复、到达生效时间或到达失效时间；
- 设备启用现金面额与当前价格档位的交集发生变化。

只要最终有效载荷变化，设备就会收到更高版本的完整配置。服务端不会发送局部增量，设备也不能把新旧
版本合并。关闭版本固定为 `cashAcceptanceEnabled=false`、`cashSaleItems=[]`；恢复版本包含当前有效
面额的完整列表。服务端可能因消息重复或失败补偿再次触发同一业务重算，但等价载荷不会无意义递增版本。

设备处理要求：

1. 新 `configVersion` 必须作为一个完整、不可分割的配置版本保存；
2. 新版本校验或硬件应用失败时立即关闭验钞器，并回 `failed + configVersion`；
3. 禁用版本应用成功后不能回退使用旧启用版本；
4. 恢复启用必须等待新的启用版本，不能根据 bootstrap `available=true` 自行恢复旧配置；
5. 指令处理成功后回执版本，服务端只有确认应用版本与最新发布版本完全相等时才可能在 bootstrap 开放
   现金入口。

### 11.2 现金进入钱箱

只有验钞器确认现金已经不可逆进入钱箱后，设备才发布 `accepted`：

```json
{
  "eventNo": "CE-A-20260729-000001",
  "eventType": "accepted",
  "cashMediumType": "banknote",
  "denominationAmount": 100,
  "cashCount": 1,
  "cashSaleTierNo": "MCST...",
  "configVersion": 12,
  "timestamp": 1785290000000
}
```

当前 `cashCount` 固定为 1，不支持多枚累计支付和找零。平台无响应时必须使用完全相同的 `eventNo` 和 payload 重试，禁止换事件号。

平台会下发 `cash_event_response`，其状态只用于展示和重试控制。设备仍然只能在收到合法 `dispense_marbles` 后出珠。

### 11.3 真实退币

只有原现金被设备机构真实退还顾客后才能上报 `returned`：

```json
{
  "eventNo": "CE-R-20260729-000001",
  "eventType": "returned",
  "relatedEventNo": "CE-A-20260729-000001",
  "cashMediumType": "banknote",
  "denominationAmount": 100,
  "cashCount": 1,
  "timestamp": 1785290003000
}
```

线下人工退现不能伪造为设备退币。同一原现金事件最多只能有一个有效 `returned`，重试必须复用原退币 `eventNo`。

## 12. 本地幂等和断网恢复

这是设备端最重要的安全要求。设备至少持久化：

- 当前 MQTT 凭证和已应用配置版本；
- 未完成现金事件的 `eventNo` 和原始 payload；
- 指令的 `messageId`、`commandType`、`operationNo` 和 `operationToken`；
- 物理动作是否已启动；
- 出珠或收珠真实计数；
- ACK、终态 `eventNo` 和完整终态结果；
- 每条待确认回执的 `sourceMessageId`、`eventNo`、`resultStatus`、原始 payload 和业务确认状态。

重连顺序固定为：

```text
重新认证并连接
-> 订阅本机 command/#
-> 发布 heartbeat 和 status
-> 补发未确认的现金原事件
-> 补发已经完成但平台未确认的终态
```

现金事件按 `cash_event_response` 的既有状态控制重试；所有 `command-result` ACK 和终态按 `command_result_ack` 控制重试。收到 MQTT PUBACK 不能删除记录，只有收到匹配的 `receiptStatus=recorded` 后才能删除本地待补发回执。恢复过程不得再次执行已经启动或完成的物理动作。无法确认动作事实时停止自动操作，保留现场证据并转人工处理。

## 13. 运维协议

业务主链通过后再对接本节。

### 13.1 拉取日志

设备收到 `command/task` 且 `commandType=collect_log` 后：

1. 使用原 `messageId` 回 ACK。
2. 按指定时间和类型收集脱敏日志并压缩。
3. 使用当前 MQTT 密码对 HTTP 上传请求做 HMAC-SHA256。
4. 上传到任务指定地址或 `/api/file/public/device-log/upload`。
5. 上传成功后回 `success`，失败回 `failed`。

日志不得包含 MQTT 密码、身份私钥、完整取珠码、会员隐私或 `operationToken`。

### 13.2 APK 和固件升级

设备收到 `command/upgrade` 后保存 `messageId`、`taskId` 和 `recordId`，校验版本、下载地址、MD5、文件大小和 `forceUpgrade`，并通过 `report/upgrade-progress` 上报：

```text
pushed -> downloading -> installing -> success / failed / skipped
```

升级失败不能破坏旧版本启动、设备身份和 MQTT 凭证。升级完成后通过 `status` 上报新版本。

## 14. 联调顺序

设备同事按以下顺序配合，不要并行制造多个物理场景：

1. 冻结最终应用包名、签名证书和安全存储方案。
2. 当前设备生成并持久化最终身份密钥，后端轮换公钥。
3. 平台授权 MQTT 凭证恢复，验证新凭证、完整 `mqttTopics`、重启和同包名覆盖升级。
4. MQTT 登录、订阅、心跳、状态、现金配置同步和测试故障上报。
5. 一个低数量平台套餐凭证，验证完整出珠和重复指令不重复出珠。
6. 一个低数量会员存珠，验证真实计数、重复终态和重启恢复。
7. 现金正常出珠、重复事件、断网、零/部分出珠、迟到终态和真实退币。
8. 最后验证日志拉取和升级，不干扰业务主链。

## 15. 通过标准

- 设备只接受本机合法 Topic 和指令。
- 页面、核销响应、支付结果和现金面额都不能直接驱动出珠。
- 相同 `messageId` 永远不会产生第二次物理动作。
- 相同 `eventNo` 永远不会产生第二次平台入账或业务处理。
- ACK 不等于完成，终态数量永远来自真实设备计数。
- MQTT PUBACK 不等于业务确认，`command-result` 只有收到匹配的 `command_result_ack.recorded` 后才能停止补发。
- 出珠、收珠、现金和退币在断网、重连、进程重启后仍可恢复原事实。
- 任何未知结果都进入人工处理，不伪造零数量、不自动重试物理动作。
- 日志和联调材料中没有设备密钥、一次性令牌和会员敏感信息。
