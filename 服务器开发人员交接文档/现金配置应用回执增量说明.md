# 现金配置应用回执增量说明

本文补充 `sync_cash_configuration` 从设备接单、应用到平台确认入库的完整回执约束。现金配置字段、
版本选择和硬件应用规则仍以[现金开关与运行可用状态增量说明](现金开关与运行可用状态增量说明.md)
为准。

## 1. 必须上报的原因

平台通过设备专属 `pxd/v1/device/{deviceNo}/command/config` 下发完整现金配置。MQTT QoS 1 的
PUBACK 只能证明 Broker 收到消息，不能证明设备已经保存配置，更不能证明验钞器已经成功应用。

设备必须通过以下 Topic 上报接单状态和最终应用结果：

```text
pxd/v1/device/{deviceNo}/report/command-result
```

平台只有处理 `status=success` 且回执中的 `configVersion` 与下发版本一致后，才会推进
`appliedConfigurationVersion`。没有成功终态时，设备屏 bootstrap 不应把该版本视为已经应用。

## 2. 固定处理顺序

```text
收到 sync_cash_configuration
-> SDK 校验 Topic、设备号、命令类型和完整载荷
-> 按 messageId 幂等登记指令，并把新版本保存为 pending
-> 上报 ack + 当前指令 configVersion
-> 串行执行禁用或 CashConfigurationAdapter.apply
-> 成功：原子标记 applied、切换当前版本并保存 success 终态
-> 失败：标记 failed、关闭验钞器并保存 failed 终态
-> 发布终态
-> 收到平台 command_result_ack(recorded)
-> 删除对应的本地待补发回执
```

`ack` 只表示设备已经可靠接单，不表示现金配置已经生效。只有 `success` 才表示完整配置已经持久化且
硬件应用成功。禁用配置的 `success` 表示禁用版本已经持久化并且验钞器已经关闭。

## 3. ACK 报文

设备可靠保存原始指令和 `pending` 状态后上报：

```json
{
  "messageId": "msg-cash-config-001",
  "commandType": "sync_cash_configuration",
  "status": "ack",
  "eventNo": "evt-cash-config-001-ack",
  "configVersion": 12,
  "timestamp": 1785729600000
}
```

现金配置 ACK 必须携带当前指令的 `configVersion`。通用
`DeviceCommandResult.acknowledgement(command, eventNo, timestamp)` 不会自动填充该字段，现金配置不能
使用这个物理指令便捷方法。应使用现金配置专用工厂：

```java
DeviceCommandResult ack = DeviceCommandResult.configurationAcknowledgement(
        command, ackEventNo, System.currentTimeMillis());
```

## 4. 成功终态

只有本地事务已经提交，并且 `CashConfigurationAdapter.apply` 或禁用动作确认成功后才能上报：

```json
{
  "messageId": "msg-cash-config-001",
  "commandType": "sync_cash_configuration",
  "status": "success",
  "eventNo": "evt-cash-config-001-success",
  "resultCode": "CASH_CONFIGURATION_APPLIED",
  "resultMessage": "现金配置已应用",
  "configVersion": 12,
  "timestamp": 1785729601000
}
```

成功终态不得携带伪造的 `actualQuantity`。`configVersion` 必须来自当前 MQTT 指令，不能填写设备本地
更高版本或 bootstrap 返回的版本。

使用现金配置专用工厂生成成功终态，SDK 会从当前强类型指令提取 `configVersion`，且不会生成
`actualQuantity`：

```java
DeviceCommandResult terminal = DeviceCommandResult.configurationTerminal(
        command, terminalEventNo, true,
        "CASH_CONFIGURATION_APPLIED", "现金配置已应用",
        System.currentTimeMillis());
```

## 5. 失败终态

协议校验、版本判断、持久化或硬件应用任一步失败，都必须保持或切换为禁用现金接收，并上报：

```json
{
  "messageId": "msg-cash-config-001",
  "commandType": "sync_cash_configuration",
  "status": "failed",
  "eventNo": "evt-cash-config-001-failed",
  "resultCode": "CASH_CONFIGURATION_APPLY_FAILED",
  "resultMessage": "现金配置应用失败",
  "configVersion": 12,
  "timestamp": 1785729601000
}
```

`resultCode` 应使用稳定、可检索且不超过后端字段边界的错误码，`resultMessage` 应说明实际失败阶段，
但不得包含 MQTT 密码、密钥、签名、原始敏感载荷或硬件凭证。

失败终态使用同一个专用工厂，并把 `successful` 设为 `false`：

```java
DeviceCommandResult terminal = DeviceCommandResult.configurationTerminal(
        command, terminalEventNo, false,
        "CASH_CONFIGURATION_APPLY_FAILED", "现金配置应用失败",
        System.currentTimeMillis());
```

## 6. 平台业务确认

平台处理每条 `command-result` 后，通过设备已经订阅的
`pxd/v1/device/{deviceNo}/command/control` 下发 `command_result_ack`：

```json
{
  "messageId": "msg-command-result-ack-001",
  "deviceNo": "VMIT03828355QAOC",
  "commandType": "command_result_ack",
  "timestamp": 1785729602000,
  "data": {
    "sourceMessageId": "msg-cash-config-001",
    "eventNo": "evt-cash-config-001-success",
    "commandType": "sync_cash_configuration",
    "resultStatus": "success",
    "receiptStatus": "recorded",
    "code": "COMMAND_RESULT_RECORDED",
    "message": "平台已持久化该指令回执",
    "retryable": false
  }
}
```

- `recorded`：设备可以删除匹配 `sourceMessageId + eventNo + resultStatus` 的本地 outbox 记录；
- `rejected`：设备保留记录，并使用相同 `eventNo` 和完全相同的原始 payload 重试；
- 不得为 `command_result_ack` 再上报 `command-result`，否则会形成确认循环；
- ACK 与终态使用不同 `eventNo`；同一条回执重试必须复用原 `eventNo` 和原始 payload；
- 收到重复 `messageId` 时不得再次应用硬件，只能重发已经保存的 ACK 或终态。

## 7. 联调通过标准

1. 平台下发版本 12，设备 ACK 和终态都带 `configVersion=12`；
2. `ack` 到达后平台只记录已接单，不推进已应用版本；
3. `success` 到达后平台的 `appliedConfigurationVersion` 推进到 12；
4. `failed` 到达后平台记录失败原因，设备验钞器保持关闭；
5. 设备收到每条回执对应的 `command_result_ack(recorded)` 后才删除 outbox；
6. 断网、重连和进程重启只补发原报文，不产生第二次配置应用。
